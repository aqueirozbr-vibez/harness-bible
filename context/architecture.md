# Harness Bible Interactive — Architecture

Sources: `specs/TRD — Harness Bible Interactive.pdf` (v0.1, traces to PRD 2026-09-21 and UI package v0.9.0), `specs/PRD — Harness Bible Interactive.pdf`, `docs/design/`. Companion: `context/project-overview.md`.

The product is the book's harness applied to the book. Each non-stack component is the one the corresponding chapter of the book describes, and the chapter is its design document. Where this file says "chNN" it means that chapter.

The folder map in section 3 is not in the TRD; it is derived from the TRD's containers and the Next.js App Router layout already in this repository.

## 2. Containers, deployment and network

### 2.1 Containers

One web application, one database, one gateway, one workflow engine, one sandbox pool. All inside the residency boundary, region São Paulo (`sa-east-1`).

| Container | Technology | Responsibility | Talks to |
|---|---|---|---|
| Next.js app (× n) | App Router, RSC, route handlers | Every user-facing screen; REST API; starts and signals workflows; authorises through OPA; creates, runs and kills sandboxes | PostgreSQL (Prisma), Temporal (start/signal/query), OPA (localhost), sandbox control API, Keycloak, object storage, OTel |
| Agent workers (× n) | Temporal workers (the engine arrives with unit 45, feature-specs/28) beside their private HTTP surface | Sensors, evidence fetcher and grader, adjudicator, assistant loop, the researcher's planner and reader, the merge's Git adapter. The only container that calls the gateway, and the only one that fetches a URL a stranger chose | Gateway (per-account virtual key), Temporal (task queues `hb-improve`, `hb-research`), PostgreSQL (read anchored text, write verdicts), object storage, the open web through `workers/fetch/` alone, the book's Git repository |
| Content pipeline | Worker in the web tier | Git release → rows; render hash; embeddings and tsvector; opens PR branches for accepted changes | Book Git repo (read deploy key; separate write-scoped key), PostgreSQL |
| Sandbox orchestrator | Firecracker pool controller | One microVM per IDE session; snapshot restore; watchdog (wall clock, memory); egress rules on the host | Sandbox hosts; object storage via signed URL only |
| PostgreSQL | primary + replica, private subnet | All relational data and the search index | — |
| Object storage | A directory behind `lib/storage/` for now (unit 49b, 2026-10-06); the S3 API, region-pinned, when a bucket exists | Uploads, saved runs, audit packs, lab file snapshots | — |
| Temporal | self-hosted (compose `temporal`, built in unit 45a: the server image with a schema step and a namespace step that each run once; feature-specs/28 § 11), its history in two databases of its own (`temporal`, `temporal_visibility`) in the same PostgreSQL server | Suggestion, evidence-grading, merge, export and research workflows; curator and endorsement signals; timers. The assistant's turn is not a workflow (feature-specs/27 § 8) | PostgreSQL (its own persistence) |
| OPA | sidecar per API pod | Roles, change classes, tenant checks; fail-closed | Decision log → Loki and ledger |
| LiteLLM gateway | self-hosted | Budgets, routing, pinning, cost; provider keys live only here | Model providers (HTTPS egress allow-list) |
| Keycloak | identity broker | SSO (SAML/OIDC) to customer IdPs; verified contributor identity | Customer IdPs |
| Observability | OTel Collector, Langfuse, Grafana/Loki/Tempo | Traces, cost, dashboards. The collector is the one road to Langfuse and the only holder of its keys (feature-specs/49 § 4, § 5.5) | The collector: Tempo and Loki; Langfuse, through its second traces pipeline, which keeps only what its two allow-lists name. The product and, from unit 80, the gateway export to the collector; Tempo receives no gateway span |

External systems: the book Git repository (source of truth; pinned releases; PRs), model providers (reached only through the gateway), customer SSO IdPs, CI runners (lab suite on every merge; results by HMAC-signed webhook), e-mail (decisions, throttles, rubric changes). Since 2026-10-05 also the open web, in two ways and no third: pages the evidence fetcher opens (a conduit of § 2.2), and pages the model provider's search and fetch tools read at the provider, on the researcher's call. On this machine the book's repository is a local Git repository the operator makes (`BOOK_REPO_DIR`, feature-specs/37 § 3); a hosted repository, its pull requests and its CI webhook are deferred until the book has a host, and e-mail until a mail service exists (feature-specs/35 D3).

Tenancy: all tenants share the web and data tiers. Isolation is by `organisationId` on every account-scoped row and by OPA policy, not by deployment. The sandbox pool is a separate VPC with no route to the data tier. The EU region exists in the admin screen as a disabled option and in no infrastructure.

Sandbox egress path: user code → the microVM's single TAP interface → host nftables with default DROP → forward only when destination is in the allow-list on 443, else DROP and log `{session_id, dst, ts}` to the `egress_denial` table → the IDE status bar shows "N requests denied by allow-list". The host, not the guest, holds the rules. Repeated denial patterns feed sandbox-abuse detection (section 8).

### 4.2 Data model domains

One Prisma schema, four domains, read left to right from accounts to content to activity to improvement:

- **Accounts**: `Organisation` (seatLimit, residency `BR_SAO_PAULO`, ssoIssuer, tokenCap, ideMinutesCap) → `User` (role, identityVerified, provenanceConsentAt, locale, throttledUntil, deletedAt) → `Seat`, `Session`.
- **Content**: `Release` (id `"2026.09"`, gitSha, renderHash) → `ChapterVersion` (semver, sourceLang, verifyStatus, redteamStatus, redteamOpen, verifiedAt, contentHash) → `Section` (layer enum of nine, ordinal 1..9, bodyEn, bodyPt), `Edition`, `SourceRow` (tier, verifiedAt, fastMoving), `Lab` (expectedRuntimeS, wallClockCapS 600, cpu 2, memoryGiB 4, declaresModelCalls, egressExtra) → `Figure` (value, unit, tier, fastMoving, scenarioParam, sourceRowId) → `DeriveLink` (labId, filePath, line, expression).
- **Activity**: `Conversation` → `Message` (mode, refusalCause, guideVersion, modelId, firstTokenMs, tokensIn/Out, traceId) → `Citation`, `SensorVerdict`, `Flag`; `LabRun` (verdict REPRODUCED / NOT_REPRODUCED / KILLED / ERROR, killReason, sharedToken) → `LabRunDiff` (MATCH / DIVERGE / NEW), `SandboxSession` (vmId, readyMs, egressDenials, modelTokens).
- **Improvement**: `Suggestion` (changeClass, state DRAFT → SUBMITTED → INTAKE_DECLINED | GRADED → SENSED → DECIDED → CURATOR_QUEUE → MERGING → MERGED → CLOSED, score) → `Anchor` (1:1, kind SECTION / FIGURE / SOURCE_ROW, existsAtVersion), `EvidenceItem` (kind, fetchStatus, tier A–G/U, baseScore, relevance, recency, independence, adjustedScore, gradedBy), `Adjudication` (decision, score, acceptAt, floorAt, sufficientTier, failingSensor, guideVersion, modelId, rubricVersionId) → `CriterionVerdict`; `CuratorAction` (overrideCode, note, seeded); `RubricVersion` → `Threshold` per change class; `LedgerRecord` hangs off both `Suggestion` and `ChapterVersion`. As planned on 2026-10-05 the build's schema is feature-specs/29 § 3, which differs from this sketch in eight named ways (29 § 8): anchors by string, a suggestion's own sensor verdicts, `ChangeKind` and `CuratorReason` beside the class, `origin`, a nullable contributor, a calibration table and a roster table.
- **Research** (Capability 5): `ResearchRun` (messageId, state, skip reason, gap, the cited sections, the brief until purged) → `ResearchFinding` (outcome INVALID / DUPLICATE / REFUTED / PROPOSED, suggestionId). A finding that is valid becomes a `Suggestion` of origin `RESEARCHER`, which belongs to the improvement domain and carries nothing of the reader.

Rules the schema itself enforces:

| Rule | Mechanism |
|---|---|
| A derived figure changes only with its derive script | `Figure.tier = DERIVED` requires a `DeriveLink`; `Threshold(DERIVED_FIGURE)` has `acceptAt = floorAt = 100`; `MergeWorkflow` refuses a derived-figure change whose branch does not touch `DeriveLink.filePath` |
| No free-text suggestion | `Anchor` is a required 1:1 on `Suggestion`; the intake sensor sets `existsAtVersion` and declines when false |
| Contributor identity retained with consent | `identityVerified` and `provenanceConsentAt` both required before `state` leaves `DRAFT`; delete sets `deletedAt` and the ledger keeps `actor` as a pseudonym |
| A researcher's suggestion is never merged on a model's word | `Suggestion.origin = RESEARCHER` has no `userId`; the workflow moves it to `MERGING` only on a `curator` record of action `ACCEPT`, and OPA denies `service:adjudicator` the `decide` action on it (invariant 32) |
| Scenario parameters and structure are curator-only | `Figure.scenarioParam = true` or `Anchor.kind = SECTION` on a structural change forces `changeClass = CURATOR_ALWAYS` at intake |
| Score is the strongest item, not the sum | `Suggestion.score = max(EvidenceItem.adjustedScore) + corroboration` in one SQL statement |
| Figures identical across editions | `Figure` hangs off `Section`, not `Edition`; both editions render the same rows |
| Content matches the release | `Release.renderHash` compared to CI's value on deploy; mismatch blocks the release |

### 4.3 Hash chain

- Canonical form: RFC 8785 JSON Canonicalization Scheme over `{seq, kind, actor, suggestionId, chapterVersionId, payload, createdAt, prevHash}`.
- `hash = sha256(canonical(record))`, hex, lower-case. Genesis: `prevHash = sha256("harness-bible-ledger-genesis")`.
- One chain for the whole ledger ordered by `seq`. A per-suggestion or per-chapter view is a filter, not a separate chain.
- Record kinds and what they cover: `submitted` (anchor, change, evidence metadata, rationale hash); `graded` (per-item tiers and adjustments); `sensors` (verdicts); `decided` (decision, reasons, guide and rubric versions, model id); `curator` (action, override code, note hash); `merged` (branch, commit sha, version from → to); `answer` (assistant message id, citations, verdicts); `export` (scope, range, head hash). Since unit 46c (feature-specs/29 § 5) the six improvement kinds have strict payloads and two kinds are added: `research` (one per run: its sections, counts and outcomes, and no suggestion, message or reader) and `endorsed` (a reader put their name to a research proposal, or took it back). Since unit 63b (migration `20261011120000_suggestion_withdrawn`) the enum also holds `RETRACTED`, a contributor's withdrawal of a suggestion that waited for a person (feature-specs/45 § 5): since unit 63c its payload says from where and under which decision, its record is a person's about the suggestion, and the audit pack's adjudications select it; nothing writes one before 63e. Since unit 62b (migration `20261011150000_conversation_erased`) it also holds `ERASED`, a reader's deletion of a conversation (feature-specs/45 § 3.7, D2): since unit 62d its payload names the conversation by id with a step key one a conversation (`erasedStepKeyOf`, found by `erasedRecordAt`), its record is a person's about nothing, and the audit pack's answers select it; nothing writes one before 62h. Since unit 68 (feature-specs/48 § 15): `research` is also a person's run's record, signed by the person who asked and paid, with its conversation, the normalised question's hash, the report's hash, the writer's model and the planner's refusal (`planned: refused`, ended `REFUSED` with the cause as a code, `R_SCOPE` or `R_PERSONAL`), and its findings' outcomes `INVALID` and `VALID`; `ERASED` and `export` take a `research` scope, a person's research conversation by id.
- Verification: recompute each hash from `seq = from` to `to`, check each `prevHash` equals the previous `hash`, check the last equals `AuditExport.headHash`. The Improve-Record "chain verified" line runs this on the filtered set plus the two chain neighbours outside it.
- Export: JSONL, one canonical record per line, then a trailer `{headHash, fromSeq, toSeq, exportedAt, signature}` signed with the platform export key. A per-chapter export includes each record's predecessor `seq` and `hash` even when the predecessor belongs to another chapter, so gaps verify without the other chapter's payloads.
- Payloads carry hashes of free text (rationale, curator note), not the text.

### 4.4 Retention and deletion

| Data | Retention | Mechanism |
|---|---|---|
| Assistant message text | 30 days | Nightly job sets `Message.text = null` and `Conversation.textPurgedAt`; citations, verdicts and metrics stay. The model's sentences in a stored mode result go with the text (a walk's explanations, a lab's two lines, a compare's open point, a brief's decision and condition; `lib/assistant/purge.ts`, 2026-10-03), and so does a citation's `claimText`; the script's numbers, the run's table and a brief's stance are metadata and stay |
| Conversation metadata | Life of account, or until its reader deletes the conversation (since unit 62e) | Rows stay for metrics and the calibration set. "Detached" is neither a message nor a research conversation (feature-specs/48 § 17.2; unit 70): the sweep never takes a person's live research, it keeps a sent finding while its `finding:<id>` workflow runs, and it then deletes the detached findings that are no proposal of the asker's. The ledger keeps every record |
| Ledger records | Never deleted | Payloads carry hashes of free text; actor is a pseudonymous user id |
| Contributor identity | With consent, life of account | `provenanceConsentAt`; withdrawal blocks new suggestions and pseudonymises the user in exports |
| A reader's words in research | 30 days, with the message | The nightly purge also empties `ResearchRun.brief` and `Message.uncovered`; no workflow history ever held them (invariant 35); the model provider received the redacted question once, in the planner's call |

### 4.5 Content pipeline

Git tag `release/2026.09` → parse chapters, labs, registries → rows (`ChapterVersion`, `Section`, `Figure`, `SourceRow`, `Lab`) → build tsvector → `renderHash = sha256` of ordered row hashes → equals CI's hash? yes: release published, reader switches; no: blocked, alert. Ingestion is idempotent per `gitSha`.

The section vectors are not part of this flow: `npm run embed:release` fills `Section.embedding`, `embeddingModel` and `embeddedAt` in the workers under `EMBED=1` after the release is ingested (feature-specs/12 § 4.2, D3; corrected review round 2, 2026-09-24), which is why those three columns are outside `renderHash` and why publication does not wait for them: the hash covers the ingested rows alone and still gates the release.

Flow back: an accepted change opens branch `improve/S-36-0198` in the book repository through the pipeline's write key; CI runs the lab suite; a curator merges; the version bumps by the book's rule (patch for wording and figures, minor for a new section, major for structure); the next release tag re-runs ingestion. The SaaS never edits content rows outside this path, with the one exemption invariant 3 names (the embedding job's three columns under `EMBED=1`).

Migrations: Prisma Migrate, forward-only, one per PR; a release that needs a schema change ships the migration first, then the content. Seeding: a fixture release built from chapters 21, 28 and 37 and their labs, rubric v1.2, and the four PRD worked examples as suggestions.

## 5. Auth and access model

### 5.1 Authentication

- Browser → `/[lang]/login` → `GET /api/v1/auth/login?idp=` → Keycloak OIDC authorize (PKCE, state, nonce, `kc_idp_hint`) → Google or GitHub (Phase 1; a customer SAML/OIDC IdP is one more Keycloak identity provider later) → Keycloak id token with the `idp`, `hb_role`, `hb_verified` and `org` claims → `GET /api/v1/auth/callback` verifies it, resolves or creates the `User` by `keycloakSub` then e-mail, and sets the `hb.session` cookie (`__Host-hb.session` in production) backed by a `Session` row (feature-specs/08 § 5.2, 09 § 4; built 2026-09-22).
- Individual accounts are the only kind in Phase 1: every new sign-in is a `READER` with no organisation; roles are mirrored from Keycloak at every sign-in and never written by the application. One exception, outside production only (unit 46e, feature-specs/29 § 6.4, § 15): the development provider stands where Keycloak stands, and may be asked for an account's role and verification.
- The realm is code: `infra/keycloak/realm-harness-bible.json` (09 § 3.2). Without Keycloak, `AUTH_DEV_PROVIDER=1` enables `GET /api/v1/auth/dev` outside production, with optional `role` and `verified`; the function that writes them (`resolveDevUser`) refuses on its own where the provider is off. Where it is on, the account page's role row is a switch whose segments are that sign-in (29 § 16); in production the row is text.
- Contributor identity verification is a Keycloak attribute surfaced as `User.identityVerified`. Anonymous suggestions are not accepted because provenance is part of the evidence.
- Public edge signs a header that only the web tier accepts; services authenticate to each other with mTLS and per-service database roles.

### 5.3 Authorisation

Route handler → OPA input `{subject, action, resource, context}` → Rego policy with default deny → allow: handler runs; deny or OPA unreachable: 403 plus a decision log entry. Built 2026-09-22 (unit 22, feature-specs/09 § 5): `lib/policy/opa.ts` asks the sidecar at `OPA_URL` with a 200 ms timeout and one retry; `lib/api/handler.ts` asks between the session and the endpoint; every server action asks through `requireAllowed` before its write; the policies are `policies/hb/*.rego` with `policies/tests/`; a deny is also an `AuthEvent` row (`policy_denied`).

- Curator-only classes are a policy rule, not application code: `changeClass == CURATOR_ALWAYS` denies `decision` to `service:adjudicator` and allows it only to a curator whose roster includes the chapter's part. Built in unit 46d (feature-specs/29 § 6, § 14): `policies/hb/improve.rego`. The subject carries `verified` and, for a curator, the roster's `parts`, both from the session; the roster is rows read for each request (`CuratorRoster`, written by `npm run roster:set`), never part of the bundle. The adjudicator is also refused a researcher's proposal (invariant 32), and a curator their own suggestion. Suggestions, curation and proposals are exempt from the tenant rule and readable only by whom their own rules name.
- Policy is versioned in Git with the rubric and loaded as an OPA bundle; a failed bundle load keeps the last good bundle and alerts.
- A stored object is reached by its signed URL alone (unit 49b, 2026-10-06; feature-specs/32 § 5, § 15): the resource kind `object` is permitted to anyone on `read` and `write` in `public.rego`, because the storage route verifies the signature — one key, one method, ten minutes, under `OBJECT_STORE_SECRET` — before the policy is asked, and the URL is handed out only by an endpoint the policy allowed on the suggestion. The policy is still asked, so the decision log has the object.
- Tenant isolation: `organisationId` on every account-scoped row; a Prisma client extension adds the tenant filter to every query; OPA denies cross-tenant reads; signed URLs are scoped per object. Raw SQL paths bypass the extension, so raw SQL is reviewed and listed.

### 5.5 Budget enforcement (ch23)

- Each organisation has one LiteLLM virtual key with `max_budget` set to the monthly cap (tokens converted to cost at pinned prices) and a per-key `tpm` limit. The gateway refuses the call before it reaches a provider. No application code counts tokens for enforcement.
- The gateway is code (unit 25a, 2026-09-23; feature-specs/11 § 3): `infra/gateway/litellm.yaml` maps the aliases `hb-frontier`, `hb-small`, `hb-embed`, `hb-rerank` to `anthropic/claude-opus-5`, `anthropic/claude-haiku-4-5`, `voyage/voyage-3`, `voyage/rerank-2`; the application names an alias, never a provider model, and a pin change is a reviewed configuration release. The proxy's own cost map at the pinned image prices those ids, so it tracks spend itself; `lib/gateway/prices.ts` (25c) repeats the prices for the ledger only.
- The client is code too (unit 25c, 2026-09-23; feature-specs/11 § 5): every call goes through `lib/gateway/client.ts` `callModel`, which decrypts the principal's key, names the alias, stamps the principal as `metadata.user_id`, applies the purpose's timeout, and writes one `BudgetLedger` row and one span line whatever the outcome (`ok`, `budget`, `unavailable`, `refused`, `provider_refusal`). The proxy's budget refusal arrives as HTTP 429 and becomes `BudgetExceededError` with the first of next month as `resetsAt`, never retried; a connection failure, timeout or 5xx after the row's own attempts (feature-specs/11 § 5.3: two retries by default, one for the classifier) is `GatewayUnavailableError` (fail closed); no `GATEWAY_URL` or no key is the same error before any request.
- Labs declare model calls in their README (`Lab.declaresModelCalls`); such a sandbox receives a session-scoped sub-key with a per-run allowance; every other sandbox receives no key.
- Every gateway response writes `BudgetLedger` (kind: assistant · grading · adjudication · lab) through the OTel pipeline; the Account-Admin meter and the IDE status bar read the same rows. The first reader is the account page's own meter (unit 35b, 2026-10-04; feature-specs/21 § 4): `lib/db/budget.ts` groups the month's rows by kind inside the principal's tenant context, `lib/budget/view.ts` turns them into every number the instrument prints, and the page never calls the gateway (invariant 6). Its unit is the cap's own: the month's cost counted at the frontier input price (`tokensOfUsd`, 11 D3 read backwards), so percent used is cost over budget, which is what the gateway compares before it refuses; a raw token count would reach 100% at some other moment.
- At the cap: the assistant returns 402 "Model budget reached for this organisation; resets 01 Oct"; model labs run without model calls and say so; adjudication of that organisation's suggestions is queued until reset, with the 24-hour target restarting from reset.
- Research is paid for by the person who asks for it (feature-specs/48 § 7, A3; Andre, 2026-10-12; unit 70): a person's run's planner, reader and writer (kind `RESEARCH`) and its retrieval's embedding and re-rank (naming the run as their `ref`) are charged to their own principal, their organisation's or their own, as their Assistant turn is. At their cap the run ends — `SKIPPED · BUDGET` at the planner, not counted toward the 30 a day; `FAILED · BUDGET` later, with what it has — and never waits; the reset is remembered on the run for the start's 402. What is left of the platform's `RESEARCH_PRINCIPAL` (an ordinary organisation the operator names, whose key's `max_budget` is US$ 20 a month to begin with, marked `Organisation.researchPrincipal`, one at most, which the research views read as the platform's payer) is Improve's vetting of the findings people send as researcher proposals, the legacy runs still in flight, which wait at its cap as before (feature-specs/40 § 7), and `npm run research:check`.

### 6.4 Client-visible transport rules

- Assistant: SSE from `POST /api/v1/assistant/conversations/{id}/messages`. The stream carries tokens, then a final event with citations and sensor verdicts. The client renders "the book does not cover this" and citation chips only from the final event, so a user never sees an uncited claim presented as cited.
- IDE: one WebSocket per sandbox session for stdin/stdout, run status and resource metrics. Close code 4001 means killed.
- Suggest form: the draft is created through `POST /api/v1/suggestions` from a client island, so the handler's limit, idempotency, policy and throttle apply (feature-specs/34 § 14); the edit page saves through `PATCH /api/v1/suggestions/{id}` a second after the last keystroke and on blur, one request at a time, and its class panel shows the class each save answers (34 § 17); its evidence list reads `GET /suggestions/{id}` every two seconds while an item is pending, and stops when none is (34 D2, § 22); evidence grading is live per item; the displayed score is a preview and the server recomputes on submit.
- Research: the `final` event of an answered turn carries `research: { state, skip?, runId? }`; the dock then asks `GET /assistant/messages/{id}/research` until the run is finished. The line and the proposal render outside the turn's answer block, which research never changes (invariant 31).
- Research on request (unit 72; feature-specs/48 § 6): the Research page asks `GET /api/v1/research/runs/{id}` every 2 s while a run is under way (`lib/hooks/useRunFollow.ts`), pausing while the document is hidden, stopping at an end, on 401, 403 or 404, and after 90 minutes, the workflow's own bound; a 429 waits its `Retry-After`. No SSE: the engine pushes nothing to the web tier, and a run lasts up to 90 minutes. A run's steps, report, pages and findings are filled into containers that are `aria-live="off"`, so the column's log announces a run's line once a state.

## 11. Invariants

Rules, not guidelines. A change that violates one is a defect regardless of test results.

**Content**
1. Content rows are never updated in place, with the one exemption invariant 3 names. A new release inserts new `ChapterVersion` rows; the reader renders only `Release.current`.
2. A release is published only when the pipeline's `renderHash` equals the hash CI computed for the same tag.
3. Content is edited only through the improvement flow: a branch in the book repository, CI, a curator merge, a release tag, ingestion. No route handler, server action or worker writes to a content table, with one exemption both the client extension and the query name (feature-specs/12 § 4.2, D3, 2026-09-23): the embedding job writes `Section.embedding`, `embeddingModel` and `embeddedAt` under `EMBED=1`, three columns the book does not contain and `renderHash` does not cover. A merge's worker (since unit 54c) starts the pipeline's ingestion and the embedding job's carry as processes of their own, each with its flag set for it alone (`pipeline/publish.ts`); the worker writes no content row itself.
4. Figures hang off `Section`, never `Edition`; the PT and EN editions render the same `Figure` and `SourceRow` rows.
5. A figure with `tier = DERIVED` has a `DeriveLink`, and a derived-figure change merges only if the branch touches `DeriveLink.filePath`.

**Model calls**
6. Only agent workers call the gateway, and only the gateway calls a provider. The web tier, the pipeline, the sandbox pool and user code never hold a provider key or a virtual key.
7. Budgets are enforced at the gateway (`max_budget`, `tpm`) and IDE minutes at the orchestrator. No application code counts tokens or minutes to decide whether a call may proceed.
8. Score arithmetic, threshold routing and change-class detection are computed in code. A model output never sets `Suggestion.score`, `Adjudication.acceptAt`, `Adjudication.floorAt` or the decision's consistency with them.
9. No environment variable, request header or config object is serialised into a prompt; the secret scanner count on prompt templates and logged prompts is zero.
10. Every model call logs its guide version, pinned model id and prompt hash; guides live in this repository under `guides/` (since 2026-09-23) and change only as a new, reviewed version.

**Agents and sensors**
11. Sensors run before any judgment. The intake sensors and the floor check run before the grader can cost a frontier call; consistency sensors run before the adjudicator; the citation sensor runs before an answer is final.
12. The adjudicator's input is assembled by the workflow from ledger rows and contains no contributor name, employer, other suggestion or curator note; identity appears only as `verified: true`.
13. `CURATOR_ALWAYS` classes (safety, OT boundary, scenario parameter, structure, rubric, new source tier) are decided only by a curator whose roster includes the chapter's part; OPA denies `service:adjudicator` the `decision` action on them.
14. An uncited claim in an assistant answer is replaced by "the book does not cover this" server-side, and the client renders citations and substitutions only from the final SSE event.
15. Each agent has a fixed cap: assistant one repair pass; grader one attempt (failure = tier U with reason); adjudicator one attempt (failure = curator queue).

**Ledger and audit**
16. `LedgerRecord` is append-only. Rows are never updated or deleted; each hash covers its payload and the previous hash; there is one chain for the whole product.
17. Ledger and calibration writes for a decision or an override are made by the workflow, not the route handler, so record and metric cannot diverge.
18. Every adjudication, override, merge, assistant answer and audit export is a ledger record, and payloads carry hashes of free text, not the text.

**Sandbox**
19. One microVM per IDE session, created on open and destroyed on close; nothing persists inside it. Saved state exists only as `LabRun.editedFiles` and logs in object storage, written through a pre-signed PUT.
20. Sandbox egress is default-deny at the host; the allow-list is package registries plus per-lab README additions; a sandbox has no route to the data tier, the gateway, or a customer network, and accepts no inbound connection.
21. A lab's verdict is computed outside the sandbox from the run's printed figures against the chapter's `Figure` rows; user code cannot produce `REPRODUCED`.
22. A sandbox for a lab that does not declare model calls receives no gateway key; a user-supplied key exists only in that session's environment and is never stored or logged.

**Access and tenancy**
23. Every `/api/v1` handler validates its input with the shared zod schema and passes OPA before touching data; OPA unreachable is a deny.
24. Every account-scoped row carries `organisationId`, every Prisma query goes through the tenant-filter extension, and raw SQL is reviewed and listed.
25. A suggestion leaves `DRAFT` only when the contributor has `identityVerified = true` and `provenanceConsentAt` set, and only with a 1:1 `Anchor` that exists at the current version. This is the rule for a person's suggestion. A researcher's has no contributor and no draft: the research run creates it `SUBMITTED` with its anchor, and invariant 32 governs it.

**Product rules**
26. No leaderboard: no query, endpoint or screen ranks contributors, counts messages per session, or measures time on page; the credit list is alphabetical.
27. No edit is attributed to the agent; contributors are credited in the chapter's improvement history. A researcher's proposal is credited to the reader who added their name, if one did, and to nobody otherwise; a contributor's draft from a finding is credited to the contributor. In both, the history's `research` mark is provenance, not credit. Since 2026-10-12 (feature-specs/48 § 8.6, unit 74, by Andre's A4: a verified contributor turns a finding of their research into a draft of their own). Until 2026-10-12 this read: "A change that began as research is credited to the reader who added their name, if one did, and to nobody otherwise; the history's `research` mark is provenance, not credit."
28. Ids, versions, hashes and code never localise; every UI string ships in PT and EN, sized for the longer edition, and nothing truncates.
29. All data, backups, observability data and the gateway stay in the São Paulo region; the EU option is disabled in the UI and absent from infrastructure. Since 2026-10-14 (feature-specs/49, Andre's L1), development telemetry of test accounts may go to Langfuse Cloud until the self-hosted Langfuse exists; production never.
30. Migrations are forward-only and additive or relaxing (a column added, or a constraint dropped so that every existing row stays valid: unit 40 dropped `NOT NULL` on `Conversation.chapter` and `contextLabel`, feature-specs/23 D4); nothing is dropped or narrowed. Rollback is by repointing `Release.current` and redeploying the previous image, never by reverting a migration.

**Researcher** (added 2026-10-05; feature-specs/27 § 4, 40 to 43)
31. The researcher never changes an answer of the Assistant, and nothing it writes is presented as the book. An assistant's answer is the same bytes whether or not research ran. Since 2026-10-12 (feature-specs/48 A1, by Andre's answer that a research is a conversation with reports): a person's research report is shown only to the person who asked, on the Research page and its dock, labelled as read from the web and not checked by Improve; a finding reaches the book only through the improvement process, and a legacy proposal is still rendered outside the answer and labelled as not part of it. Until 2026-10-12 this read: "The researcher never answers a reader … what research finds reaches a reader only as a proposal that the improvement process accepted".
32. A suggestion of origin `RESEARCHER` reaches `MERGING` only by a `curator` record of action `ACCEPT`. The adjudicator may recommend it and never decide it; a refuted one is closed with its records and proposed to nobody. The merge holds it too (unit 61b): it commits a researcher's proposal only where the accept it follows from is a curator's (`NO_CURATOR_ACCEPT` otherwise).
33. The planner reads the person's question and never anything the web wrote; the reader reads the web and never the question; the writer reads the question and the reader's notes on the pages, holds no tool, and its output is checked in code and shown only to the asker. The only text that crosses from the question's side to the web's side is the brief, after the brief sensor. No call holds a client tool. Since 2026-10-12 (feature-specs/48 A1, unit 69: a report that answers the person's question must be written by a call that holds the question, and the reader may not, so a third call writes it). Until 2026-10-12 this read: "The planner reads the reader's turn and never the web; the reader reads the web and never the turn. The only text that crosses is the brief, after the brief sensor. Neither call holds a client tool." A legacy run's two calls hold to both readings.
34. Evidence is what the product's own fetcher opened and stored. A source the researcher named, or the provider's tools read, counts for nothing until then; the fetcher is the only code that requests a URL a stranger chose.
35. No reader's or contributor's words enter a workflow's history: workflow and activity arguments and results are ids, enumerations, numbers and hashes. The link from a question to a suggestion exists only in the asker's own rows, points one way, and no ledger record of a suggestion names the asker unless that reader endorsed it.
