The scenario agent raises a maintenance work order for pump P-101 in 11 steps, three of which write to external systems. At 2,000 queries a day and an assumed worker loss of 0.4% per step ill illustrative, a task meets at least one worker failure with probability 4.3% ƒ derive L38.

That is 86 interrupted tasks a day ƒ L41. A loop that restarts from step 1 repeats five steps on average, and three in eleven of those are writes: 117 duplicate side effects a day ƒ L47. A durable workflow with idempotency keys on every write activity repeats none, which Lab 21 reproduces by killing the worker at step 7.

Retries do not remove the need for keys. you · 10:42

Why does Lab 21 still need idempotency keys if Temporal retries activities? Does Temporal Cloud bill for the replayed events?

assistant · explain · 10:42en · cites en edition v1.5.0

Retries and idempotency keys solve different problems. A retry runs a failed activity again. It cannot tell whether the failed attempt already reached the external system 21.2.

Temporal's default retry policy starts at a 1 s interval with a backoff coefficient of 2.0. A retried write without a key is a second write 21.3.

In the P-101 scenario, a loop that restarts from step 1 causes 117 duplicate side effects a day. A durable workflow with a key on every write activity causes 0 21.3. Lab 21 checks this by killing the worker at step 7 and counting duplicate writes Lab 21 · README.

The key is also what the idempotency sensor reads. It blocks a second write with the same key before the write reaches the tool 26.3.

Whether Temporal Cloud bills for replayed events: the book does not cover this. Vendor pricing today is outside the book's scope. To measure your own billing lines, use the protocol in 15.4.
