# 32 · Evidence — feature spec (the fetcher, uploads and object storage, DOIs, the evidence grader, grading on add)

Read `CLAUDE.md` and `context/ai-workflow-rules.md` before starting.

Source of truth: PRD Capability 4, requirement 2 ("fetched or opened where possible; an evidence link that cannot be opened is graded as unverifiable, not as weak") and the rubric; TRD § 2.3 ("evidence fetcher and grader"), § 6.1 (`POST /suggestions/{id}/evidence`), § 8 (the evidence grader's column) and § 10 ("fetched evidence enters the grader as fenced untrusted data"); architecture § 6.1, § 9 and invariants 6, 8, 11 and 15; the screens Improve-Suggest (the evidence items and their states) and Components (the `link could not be opened` error).

**The TRD is silent on the fetcher itself**: which process fetches, its timeouts, size limits, content types, and any protection against a URL that points inward. It lists no network conduit for it. This spec supplies all of that, and the numbers it needs are decisions (§ 12), not defaults.

Prerequisite specs: `11-model-gateway.md` (the client, the request rows), `29-improvement-schema.md` (`EvidenceItem`), `30-rubric.md` (what the grades are multiplied into), `31-suggestion-intake.md` (the draft).

Scope: tracker unit 49 (49a to 49f). Not here: the suggestion's score as a decision (spec 33), the form that shows items grading (34).

## 1. Purpose

Evidence is the only thing in a suggestion the rubric scores, and the product's claim is that it was read: "relevance graded with the source opened, not from the citation". So the product must open what a contributor points at, itself, and hand a model the document and not the contributor's description of it. Opening an arbitrary URL from inside the deployment is also the most dangerous thing Improve does, which is why the way out is one module with one job.

The researcher depends on this spec more than on any other: by answer A3 (spec 27) there is no registry of trusted domains, so the tier this grader gives a page **is** the trust decision.

## 2. Dependencies and order

49a (fetcher) and 49b (storage) need nothing and can be built in either order. 49c needs 49a. 49d needs 49a, 49b and `lib/rubric`. 49e needs 49d and the draft endpoints. 49f adds two kinds of content to 49d.

## 3. The kinds

| Kind | The contributor gives | The product does | Tier |
|---|---|---|---|
| `LINK` | an `https` URL | fetches it (§ 4), extracts its text, grades it | the grader's, B to G; `U` when it could not be opened |
| `DOI` | a DOI | resolves it, reads its public metadata, fetches the landing page (§ 6), grades it | the same |
| `UPLOAD` | a file | stores it (§ 5), grades its content | the same |
| `LAB_RUN` | a saved lab run | **refused in this build**: 422 `EVIDENCE_KIND_NOT_YET`, "saved lab runs arrive with the IDE" (candidate) | A, by rule, when Phase 3 exists |

Tier A is never the grader's to give (D3): "reproducible" is a fact the product establishes by running something, not a property a document can be classified into. Until the IDE exists the only tier A items are the fixtures of the worked examples (spec 33 § 8), and a derived-figure change cannot be accepted (spec 30 § 4.4).

## 4. The fetcher (49a, `workers/fetch/`)

One function leaves the deployment for a URL a stranger chose: `fetchEvidence(url) → { status, finalUrl, contentType, bytes, sha256, fetchedAt } | { unreachable: reason }`. It runs only in the workers. The web tier never fetches (a lint rule restricts `workers/fetch/**` exactly as it restricts the gateway client).

### 4.1 The guard (`guard.ts`, pure, tested without a network)

- `https` only, port 443 only, no credentials in the URL, a host name and not an address literal.
- The host is resolved, and **every** address it resolves to must be public: not loopback, not private (10/8, 172.16/12, 192.168/16), not link-local (169.254/16, which holds the cloud metadata address), not carrier-grade NAT (100.64/10), not multicast or unspecified, and the IPv6 equivalents. One private address among several refuses the host.
- The connection is made to the address that was checked, with the name as SNI and `Host`, so a second resolution cannot answer differently.
- A redirect is not followed by the client. Its target goes through the whole guard again, and the chain has a limit (D1).
- The deployment's own hosts are refused by name as well (`APP_URL`, the gateway, the workers, the object store, the engine), whatever they resolve to.

### 4.2 The request

No cookies, no authorisation, no referrer. A fixed `User-Agent` that names the product and a contact address, so a publisher can tell what opened their page. `Accept` lists the types of § 4.3. The body is read as a stream and abandoned at the size limit; the whole fetch has a deadline (D1). Nothing the page asks for is fetched: no scripts, no images, no frames.

### 4.3 What is opened

| Content type | Result |
|---|---|
| `text/html`, `application/xhtml+xml` | text extracted: title, the visible text in reading order, the publication date from the page's own metadata when it states one, the canonical URL |
| `text/plain`, `text/markdown` | as is |
| `application/pdf`, `image/png`, `image/jpeg` | kept as bytes for 49f |
| anything else | `unsupported:<type>` |

Extraction reuses the HTML parser the content pipeline already depends on; 49a names it, and stops under rules § 2.5 if a new dependency would be needed.

### 4.4 Outcomes

| `fetchStatus` | When | Tier |
|---|---|---|
| `opened:200` | a supported document was read | graded |
| `unreachable:<status or cause>` | 4xx, 5xx, timeout, refused by the guard, too many redirects, over the size limit | `U`, `gradedBy: "intake-rules"`, with the cause as the reason |
| `unsupported:<type>` | a type § 4.3 does not open | `U`, the same |
| `not_supplied` | an upload that never arrived | `U` |

The Components screen's error is this row: "Evidence 2 returned 403. It is graded U, score 0, not weak. The other items still count."

A page behind a login or a paywall opens as whatever it shows a stranger. The contributor can upload the document instead (TRD § 10).

## 5. Object storage and uploads (49b)

The architecture names an S3-compatible bucket in the region for uploads, saved runs and audit packs; none exists yet. This unit adds it for the two uses Improve has.

- **Compose**: a `minio` service on the internal network, loopback-published, its data on a named volume. Configuration in `lib/env.ts` without values committed: `OBJECT_STORE_URL`, `OBJECT_STORE_BUCKET`, `OBJECT_STORE_ACCESS_KEY`, `OBJECT_STORE_SECRET_KEY`.
- **Client**: `lib/storage/` with `putObject`, `getObject`, `signedPutUrl`, `signedGetUrl`. It needs an S3 client and a request signer; 49b states the packages, their size and licence and waits for confirmation (rules § 2.5), since the architecture names the store but not a library.
- **Keys**: `evidence/<suggestionId>/<itemId>/source` (what was uploaded or fetched as bytes), `evidence/<suggestionId>/<itemId>/text` (exactly what the grader read), `audit/<exportId>.jsonl` (spec 38). Keys are never guessable from a public id alone and are served only through signed URLs scoped to one object (architecture § 5.3).
- **Upload**: `POST /api/v1/suggestions/{id}/evidence/uploads` (owner) answers a pre-signed `PUT` with a short life (the sandbox's 10 minutes, architecture § 2.2) and an `uploadKey`. The browser sends the file to the store, never through the web tier. The accepted types are those of § 4.3 that are not HTML; the size limit is D2.
- **The text the grader read is kept.** Every graded item stores it under its `text` key with its sha256 in the row and in the `graded` record. A curator who doubts a grade opens what was graded, not what the page says today.

## 6. DOIs (49c)

A DOI is checked for form, then opened two ways through the fetcher: the resolver's redirect to the publisher's page, and the public metadata record for that DOI (title, type, publication date), which is read as JSON and never shown to a model as instructions. The date comes from the metadata. The text graded is the landing page's, which for a paywalled paper is its abstract; that is what the contributor's reader would see, and the grade says so. A DOI that does not resolve is `unreachable`.

## 7. The evidence grader (49d)

### 7.1 The agent

| | |
|---|---|
| Guide | `guides/grader/v1.3/` (`guide.md`, `manifest.json`), the first version of this agent in this repository, numbered as the TRD numbers it |
| Model | `hb-small`, purpose `grading` |
| Prefix, byte-stable | 1 the guide · 2 the rubric's tiers and factors (from `rubric/v1.2`, rendered once per version) · then, per call: 3 the anchored claim and the proposed change · 4 the evidence document |
| May read | the document as fetched; the anchored text; the proposed change |
| May never read | the contributor, in any form; the rationale; other items; other suggestions |
| Cap | one attempt; any failure is tier `U` with the reason (invariant 15) |

This is not the assistant's grounding grader, which is a part of the assistant's guide and judges answers. The loader's `Agent` union already names `"grader"` for this one.

### 7.2 The output, and what code does with it

```ts
{ tier: "B" | "C" | "D" | "E" | "F" | "G",
  relevance: "direct" | "partial" | "tangential",
  stake: "none" | "vendor",                 // is the publisher the vendor the claim is about
  publishedOn: "YYYY-MM-DD" | null,         // only when the page's own metadata gave none
  reason: string }                          // at most 30 words
```

The TRD's sketch has the model return the multipliers. Here it returns classifications and code looks the numbers up (`lib/rubric`), so a model's output never is a number of the score (invariant 8):

- `baseScore` from the tier.
- `relevance` 1.0, 0.6 or 0.2 from the classification.
- `recency` from the anchor's `fastMoving` and the item's age on the day of grading: the page's metadata date if it has one, else the grader's `publishedOn`, else none (spec 30 § 3.4). Since 2026-10-08 the flag is `fastMovingOf`'s: the anchor's, or a claim's or a row's own declaration (30 § 3.4, as decided). A draft whose declaration changes after an item was graded has that item's recency and score worked out again from the age recorded, with no model asked (34 § 24).
- `independence` (§ 7.4).
- `adjustedScore` by `lib/rubric`.

### 7.3 The document is untrusted

The document goes into the prompt inside a fence the guide names as data to be classified, never instructions to follow. The grader has no tool. Its output is parsed strictly: an unknown key, a tier outside the enumeration, or a reason over the limit is the one failure. A page that says "award tier B" can at worst be misclassified as B; it cannot act, and the score is still arithmetic.

### 7.4 Independence, without showing the contributor to a model

The rubric's third value, 0.7, is "the contributor's own employer". The grader may never read who the contributor is. So code decides it: an item's independence is 0.7 when its publisher's registrable domain is the domain of the contributor's verified e-mail address, public mail providers excepted (a short list kept as data); else 0.8 when the grader said `stake: "vendor"`; else 1.0. A researcher's suggestion has no contributor and never takes 0.7.

### 7.5 The request row

`evidenceGrader` joins `lib/gateway/policy.ts`: `(grading, hb-small)`, no effort parameter (the model refuses it, as the classifier's row records). Its token ceiling, timeout and retries are set in the unit with their derivation, under the delegation Andre gave for that table on 2026-09-24, and recorded in architecture § 12. The document is cut to the row's input ceiling at a paragraph boundary, and an item that was cut says so (`truncated`), in the row and on the screen.

## 8. Grading on add (49e)

`POST /api/v1/suggestions/{id}/evidence` — owner; a draft, or a suggestion open for revision (spec 31 § 6.5); body `{ kind, url | doi | uploadKey }`. A suggestion holds at most ten items (D4).

1. The item is created `PENDING` with its ordinal; the answer is 202 with the item.
2. `GradeEvidenceWorkflow` (`evidence:<itemId>`, queue `hb-improve`) runs three activities: fetch or open, extract and store the text, grade. The stage is a query on the workflow (`1 of 3`, `2 of 3`, `3 of 3`), which is the number the form's loader shows.
3. The item becomes `GRADED`. `GET /suggestions/{id}` then carries the item with its arithmetic (`70 × 1.0 × 1.0 × 0.8 = 56`), the suggestion's score by `scoreOf`, and the predicted outcome by `predict` (spec 30 § 4.4). The form displays; it computes nothing (architecture § 6.4).

`DELETE /api/v1/suggestions/{id}/evidence/{itemId}` — owner, same states; a pending item's workflow is cancelled.

The model call is charged to the contributor's principal, kind `GRADING`, `ref` the suggestion id. At that principal's cap the item stays `PENDING` and says why, with the reset date; nothing is graded `U` for lack of budget.

## 9. PDFs and images (49f)

A PDF (linked or uploaded) and an image (uploaded: the worked example's screenshot is one) are not text the product can cut and fence. They go to the grader as the provider's own document and image content, through the gateway, with the same guide and the same output. 49f first proves that the pinned proxy passes those content types on its Anthropic route and that `hb-small` accepts them; if either fails it stops under rules § 4.4 with the alternative (a text-extraction dependency for PDFs; images unsupported) for Andre to choose. Their size limits are the provider's documented ones, read in the unit and recorded, never above D2.

## 10. States

| State | What the contributor sees (strings from the screens where they exist) |
|---|---|
| grading | the item dashed, `opened · 200 · classifying tier`, the loader with its stage, `Cancel` |
| graded, opened | the tier badge, the score, the arithmetic, `opened · 200 · 12 days old`, `Remove` |
| unreachable | `link could not be opened` · `U` · the cause, `Replace evidence` |
| unsupported type | `U`, the type, and that an upload of the document would be read |
| budget cap | the item pending, the gateway's refusal and the reset date |
| workflows unavailable | the add is refused, 503; nothing is created |

## 11. Out of scope

- A registry of trusted or blocked domains (answer A3). The rubric decides.
- Honouring `robots.txt` (D5).
- Archiving a page for later (a snapshot service); the stored text is what was graded.
- Evidence of kind `LAB_RUN` from a person.

## 14. As built (unit 49a, 2026-10-06)

§ 4 as written: `workers/fetch/` — `guard.ts`, `transport.ts`, `html.ts`, `fetch.ts` — and `npm run fetch:check`. The three numbers of D1 are Andre's, decided 2026-10-06 on the recommendation ("use your recommendation"): 20 s for the whole fetch, 5 MB for the body (5 × 1024 × 1024 bytes, as the gates count kilobytes), 5 redirects. Nothing calls `fetchEvidence` yet: 49c opens DOIs through it, 49d wraps it in the grading activity.

- **The guard is pure and is two questions** (`guard.ts`): `checkUrl(raw, own)` — `https`, no port left after the parser drops 443, no credentials, a host name that is not an address literal (the parser normalises a decimal, octal or hex IPv4 to dotted, so `https://2130706433/` is caught), not one of the deployment's own, with a dot in it, not under `localhost`, `local`, `internal`, `localdomain` or `arpa`; the fragment dropped — and `checkAddresses(addresses)` — at least one, every one public. The classes refused are § 4.1's and the rest of the registries: IPv4 unspecified, private, carrier-grade NAT, loopback, link-local, the reserved and documentation and benchmarking blocks, multicast, 240/4, broadcast; IPv6 unspecified, loopback, link-local, site-local, unique-local, multicast, discard, documentation (`2001:db8::/32`, `3fff::/20`), ORCHID, segment routing, local-use NAT64, and Teredo entire (its client address is obfuscated and cannot be checked). The mapped, NAT64 and 6to4 forms are judged by the IPv4 address they carry; the deprecated compatible form is refused outright. Two refusals are the unit's beyond the spec's words and are recorded for Andre: single-label names (compose's services) and the internal suffixes. The reasons are the words of `fetchStatus` and the ledger's `FetchStatusSchema` (`lib/schemas/ledger.ts`, now exported) reads every one.
- **The deployment's own hosts** are every URL the environment holds: `APP_URL`, `GATEWAY_URL`, `WORKERS_URL`, `TEMPORAL_ADDRESS`, `OPA_URL`, `DATABASE_URL`, `KEYCLOAK_ISSUER` (`ownHostsOf`); the object store's joins in 49b. They are refused by name whatever they resolve to.
- **The connection is pinned** (`transport.ts`): `node:https` with the checked address in `host`, the name in `servername` (TLS validates the certificate against the name) and as the `Host` header, `agent: false` so no socket of a stranger's page is pooled. `requestOptionsOf` is pure and tested; `transportOf(request)` takes the request function, which is how the suite runs the same code on `node:http` against its own server. The checked addresses are tried in order until one answers; a certificate failure or the deadline ends the attempts at once.
- **A redirect is a URL back at the first question**: not followed by the client (`node:https` follows nothing), its `Location` resolved against the page, put through `checkUrl` and the resolution again, at most five times; the sixth is `unreachable:redirects`. **A target on `http:` is asked for on `https:`**, same host and path, with plain HTTP's port dropped: doi.org's own chain hops through `http://www.doi.org/…` (seen on 2026-10-06), and the fetcher never speaks plain HTTP either way — a host without TLS is then `unreachable` at the connection. A contributor's own `http:` URL is still refused by scheme. This is a choice beyond the spec's letter, recorded for Andre.
- **The request** (§ 4.2): `User-Agent: Harness-Bible-Evidence/0.1 (+<APP_URL>)` — the contact is the app's address until Andre names a mailbox or a page for publishers; `Accept` with § 4.3's seven types and nothing else, so a server that honours it answers 406 and the item is `unreachable:406`; `Accept-Encoding: gzip, deflate, br`, undone by `node:zlib` with the size limit counted on the decoded bytes (a compressed body that inflates past it is `unreachable:size`); `Connection: close`. No cookie, authorization or referrer is ever set, and nothing of one response carries into the next request. The body is read as a stream and the socket destroyed the moment it passes the limit; a declared `Content-Length` over the limit is refused before a byte is read. One `AbortController` under one timer covers every redirect and the body.
- **What is opened** (§ 4.3): `text/html` and `application/xhtml+xml` through `html.ts`; `text/plain` and `text/markdown` as they are, decoded by the header's charset, else for HTML the charset declared in its first kilobyte, else UTF-8; `application/pdf`, `image/png`, `image/jpeg` as bytes for 49f. Anything else is `unsupported:<type>` (the media type lowercased, without parameters, spelt as the ledger's pattern allows), `unsupported:unknown` when there is no usable `Content-Type`; the body is not read. A status other than 200 is `unreachable:<status>`, a 204 included. The `sha256` and the byte count are of the body as stored: after the content encoding, before any character decoding.
- **The HTML reader is the unit's own** (`html.ts`): § 4.3 said the extraction would reuse the parser the pipeline depends on, and there is none — `marked` renders markdown and parses no HTML, and no HTML parser is anywhere in the tree. Rather than stop for a dependency (rules § 2.5), the unit wrote a tokenizer of some two hundred lines: a start tag read with its attributes, quotes respected; `script`, `style`, `textarea`, `title`, `noscript`, `template`, `iframe` and their kin jumped to their closing tag so nothing they hold is text; `svg`, `math`, `object`, `select`, `canvas`, `audio`, `video` and anything `hidden` or `aria-hidden` skipped to their matching close, nested; comments, doctypes and processing instructions dropped; text collapsed as a browser collapses whitespace, a line per block, `- ` before a list item, ` | ` between cells, an image's `alt`. Named, decimal and hex character references are decoded (a table of the common names; an unknown name is left as written). The title is `<title>`, else `og:title`. The date is the page's own metadata, by how directly it states it: `article:published_time`, then JSON-LD `datePublished` (its `@graph` walked), then `itemprop=datePublished`, then the named `meta` dates (`date`, `dc.date.issued`, `pubdate`, `citation_publication_date` and the rest), then `<time pubdate>`, then any `<time datetime>`; a modified time is never a publication date; the value is kept as the day the page wrote, not shifted to UTC. The canonical URL is `<link rel=canonical>` resolved against the page fetched, else `og:url`, and only when it is `http(s)`. A page that is not well formed yields what a lenient reading gives, never an error. The alternative is `htmlparser2` (MIT) if Andre prefers a parser; the tokenizer's tests are the contract either way.
- **The outcome is a value, never a throw**: `opened` (`fetchStatus: "opened:200"`, the final URL, the redirect count, the type, the bytes, the hash, the document), `unsupported`, or `unreachable` with its `cause` and the URL at which it failed; a throw from `fetchEvidence` is a defect of the fetcher. `FetchDeps` (the resolver, the transport, the own hosts, the user agent, the limits, the clock) are the seam the suite uses; `defaultFetchDeps()` is the workers' — `dns.lookup` with every address, IPv4 first.
- **The rule** (§ 13.9): `eslint.config.mjs` gained `FETCH_PRIVATE`, `**/workers/fetch/**`, beside the group that closes `workers/` as a whole — so the fetcher stays closed should `workers/` ever be opened, and the message names this spec. It applies to the web tier, `lib/workflows/`, `lib/gateway/` and the workflow suites' helpers; the scripts may run it, as they run the workers' other code. `tests/fetch-lint.test.ts` lints a snippet under each folder.
- **By hand**: `npm run fetch:check -- <url>` runs the fetcher as the workers will and prints facts, never the page.

## 15. As built (unit 49b, 2026-10-06)

§ 5, as Andre decided it on 2026-10-06 when the unit was asked for its two answers: **"size limit 100 MB, it'll be stored locally for now, we don't have a cloud infra."** So: no `minio` service, no S3 client (D6 is moot until there is a bucket), D2 is 100 MB (not the 5 MB recommended), and object storage is a directory on the web tier's host behind the interface § 5 named, so that a bucket replaces the directory without touching a caller. The spec's four functions exist with the spec's names; the signed URLs exist with the spec's life; the one thing the directory cannot give is § 5's "never through the web tier", recorded below.

- **The store** (`lib/storage/local.ts`, `localStore(dir)`): an object is a file under `OBJECT_STORE_DIR` (default `.store`, ignored by git) at its key's path, with a sidecar `<key>.meta.json` holding its type, size, sha256 and time. A put streams the body through a meter into a part file, writes the sidecar, and renames the part into place — whole or not at all; a body that passes the size it was allowed is cut off and the part removed, and an object that was there stays. The key is checked against `ObjectKeySchema` (`lib/schemas/storage.ts`: `evidence/…` or `audit/…`, segments of `[A-Za-z0-9._-]`, never `.` or `..`, at most 200 characters) and the resolved path against the root before anything is opened: a key is never a path a person wrote. `ObjectStore` is the interface (`put`, `get`, `head`, `remove`); `lib/storage/index.ts` gives the spec's `putObject`, `getObject`, `signedPutUrl`, `signedGetUrl`, with `headObject`, `verifySignedToken` and `storageAvailable` beside them.
- **The signature** (`lib/storage/sign.ts`): an HS256 token under `OBJECT_STORE_SECRET` (32 bytes as 64 hex, in `SECRET_ENV_KEYS`, required in production, refused as `503 STORAGE_UNAVAILABLE` when unset) with `typ: hb-object`, carrying one key, one method, and for a PUT the one `Content-Type` and the most bytes it may carry, for `SIGNED_URL_TTL_S` = 600 (the architecture's ten minutes, § 2.2). `jose` signs it, as it signs the product's sessions; no new dependency. A token of another kind under the same secret, altered, expired, under another secret, for another method, or carrying a key that is not the product's does not verify.
- **The routes** (`lib/api/endpoints/storage.ts`, `app/api/v1/storage/[token]/route.ts`): `PUT /api/v1/storage/{token}` stores the bytes a PUT token allows — the body's media type must be the one signed for (`415 UPLOAD_TYPE_MISMATCH`), a declared `Content-Length` over the size is refused before a byte is read and a body that passes it while streaming is cut off with nothing stored (`413 UPLOAD_TOO_LARGE`, the limit in the detail) — and answers the sidecar; `GET /api/v1/storage/{token}` serves the object a GET token names with its type, length, hash as `ETag`, `nosniff`, `inline` with a file name, and `no-store`. Both are public routes (no session is read: the token is the whole credential, as a bucket's pre-signed URL is), limited by address as the content routes are (120 a minute), and both verify the token **before the policy is asked** — `403 SIGNED_URL_INVALID` for a token that does not verify, is expired, or is for the other method — so that a forged URL never reaches the sidecar. The PUT reads its body itself from `request.body` as a stream: the pipeline reads no body when an endpoint declares none, and `EndpointSpec` gained `raw` (`{ request?, response? }`, media types) so the OpenAPI document describes a body of bytes.
- **The policy** (`lib/policy/input.ts`, `policies/hb/public.rego`): a new resource kind, `object`, permitted to anyone on `read` and `write` and nothing else, in `public_kinds` so the tenant rule leaves it alone; two tests in `authz_test.rego`. - **The ticket** (`lib/api/endpoints/evidence.ts` `evidenceUploadCreate`, `app/api/v1/suggestions/[id]/evidence/uploads/route.ts`): `POST /api/v1/suggestions/{id}/evidence/uploads`, the owner of a draft or of a suggestion open for revision (31 § 6.5), the contributor's role, the policy's `write` on the suggestion, the suggestion's own rate (120 a minute, as its edits); body `{ contentType }` from the five types of § 4.3 that are not HTML (`UPLOAD_TYPES`); answers `{ uploadKey, url, method: "PUT", headers: { "content-type" }, maxBytes, expiresAt }`. The key is `evidence/<suggestionId>/<itemId>/source` with the item's id allocated now, so that 49e creates the item under it. A suggestion past draft and not revisable is `409 CONFLICT`; a stranger's is 404 (the door's read), a reader's 403 (the role), a curator's 403 (the policy's owner rule). Nothing is written by the ticket; one never used leaves nothing behind.
- **The deviation**: with a directory and no bucket, the browser's PUT goes to the web tier's own route, so the bytes pass through the web tier, which § 5 and architecture § 2.2 said they never would. That holds for as long as the store is a directory and is undone by a bucket, whose pre-signed URL the same `signedPutUrl` would then answer. A second web instance would need the same directory mounted; the architecture's "× n" web tier is for a bucket.
