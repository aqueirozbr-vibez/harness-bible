# Code Standards

Companions: `context/architecture.md` (stack, boundaries, invariants), `context/ui-context.md` (tokens, components, styling), `context/project-overview.md`. When a rule here conflicts with an invariant in architecture.md § 11, the invariant wins.

Current toolchain: Next.js 16.3 (App Router, Turbopack), React 19.2, TypeScript 5 with `strict: true`, Tailwind CSS 4, ESLint 9 with `eslint-config-next` (core-web-vitals + typescript), import alias `@/*` → repo root, no `src/` directory.

## General

- Keep modules small and single-purpose. A file exports one component, one workflow, one schema group, or one set of related pure functions. If a file needs a section comment to navigate, split it.
- Fix root causes. Do not layer a workaround on a bug; do not add a retry, a cast or a null check to hide a wrong type or a wrong query. Find the defect and correct it.
- Do not mix concerns. A route handler does not render; a component does not fetch from the gateway; a workflow does not format a UI string; a schema does not touch the database.
- Follow the phase ownership rule (architecture § 3.3) in the build order decided on 2026-10-05 (Reader, Assistant, Improvement, Researcher, IDE). Code for a phase must compile and run with the containers of every later phase in that order absent. Do not import from `workers/`, `sandbox/` or the gateway client in Phase 1 code: `eslint.config.mjs` refuses `lib/gateway/client.ts`, `lib/gateway/keys.ts`, `lib/gateway/embed.ts`, `lib/gateway/rerank.ts` and `workers/**` outside the workers, their scripts and the tests, so the rule is lint-enforced, not discipline (feature-specs/11 § 5.5). The web tier reaches the workers through `lib/workers/client.ts` alone.
- Every derived number, threshold, hash and decision is computed in code that has a unit test. Nothing numeric is taken from a model output, a UI string or a comment.
- Prefer deletion to abstraction. Three similar lines are better than a helper with a boolean flag. Extract only when the third caller appears and the shapes are identical.
- No dead code, no commented-out code, no TODO without an issue reference. `// TODO(#123): …` is the only accepted form.
- Write for the reader who did not write it. Names say what a thing is; comments say why, never what. British spelling in identifiers, comments and strings (`organisation`, `colour`, `serialise`).
- Match the book's vocabulary exactly: chapter, section, layer, figure, source row, derive link, lab, run, verdict, suggestion, anchor, evidence item, tier, adjudication, curator, ledger record, release. Do not invent synonyms (`article`, `note`, `proof`, `reviewer`).

## TypeScript

- `strict: true` is required and stays on. Do not add `// @ts-ignore`, `// @ts-expect-error` (except in a test asserting a type error), `as any`, or a non-null assertion `!` outside a test. `skipLibCheck` stays on for third-party types only.
- Never `any`. Use `unknown` at boundaries and narrow it with a zod schema or a type guard. Internal types are explicit `interface` or `type` aliases; prefer `interface` for object shapes that may be extended, `type` for unions, tuples and mapped types.
- Validate every external input at the boundary before trusting it: request bodies, query strings, route params, webhook payloads, gateway responses, sandbox stdout, evidence fetch results, Temporal activity inputs, environment variables. The boundary is a zod schema in `lib/schemas/`; downstream code receives the inferred type, never raw JSON.
- Types come from one source. Domain types are `z.infer<typeof Schema>` from `lib/schemas/`; database row types come from the Prisma client. Do not hand-write a type that duplicates either. Convert between them in one named mapper per direction (`toSectionDto(row)`), in `lib/db/`.
- Model every domain enumeration as a union of string literals that mirrors the Prisma enum exactly (`type Verdict = "REPRODUCED" | "NOT_REPRODUCED" | "KILLED" | "ERROR"`), exported from `lib/schemas/`. Switch over unions with an exhaustive `never` check in the `default` branch.
- Represent absence explicitly. Optional properties (`?:`) only for inputs; outputs use `T | null` so a missing value cannot be confused with an omitted key. Never use `undefined` as a sentinel for "not yet computed"; model states as a union.
- Money and tokens are `bigint` in the database and `number` only after conversion at a named boundary with a range check. Scores are integers. Multipliers (`1.0 | 0.6 | 0.2`) are literal unions, not `number`.
- Ids are branded: `type SectionId = string & { readonly __brand: "SectionId" }`, created only by a parser in `lib/schemas/ids.ts` that validates the format (`"21.3"`, `"F-21-03"`, `"21.9 r4"`, `"S-15-0377"`). A function that takes a `SectionId` cannot be passed a raw string.
- Functions are `function` declarations at module top level; arrow functions for callbacks and inline handlers only. Every exported function has explicit parameter and return types. Async functions return `Promise<T>`, never `Promise<any>` or `Promise<void>` where a result exists.
- Errors are typed. Throw subclasses of `AppError` (`lib/errors.ts`) with a `code` from the API error catalogue; never throw a string or a bare `Error` from application code. Catch at boundaries only (route handler, workflow activity, server action); do not catch to log and rethrow.
- Imports: absolute via `@/` for anything outside the current folder; relative `./` only within a folder. Order: node builtins, external packages, `@/lib`, `@/components`, relative; `import type` for type-only imports. No default exports except where Next.js requires them (`page.tsx`, `layout.tsx`, `route.ts` do not, `next.config.ts` does).
- Dates are `Date` in memory, ISO 8601 strings on the wire, `DateTime` in Prisma. Formatting happens only in `lib/i18n/format.ts`, never inline.
- `readonly` on every array and object property that is not mutated. Prefer `ReadonlyArray<T>` in function parameters.
- No enums (`enum`), no namespaces, no `class` except `AppError` subclasses and third-party integrations that require it.

## Next.js

- Default to Server Components. Add `"use client"` only to a leaf that needs browser state, an event handler, a browser API, SSE, WebSocket or CodeMirror. Keep the client boundary as low in the tree as possible; pass server data down as props, never re-fetch on the client what the server already had.
- Server Components fetch through `lib/db/` query functions, never through `fetch("/api/v1/…")` to their own API. Client Components mutate through server actions (forms) or the generated OpenAPI client (`lib/api/client.ts`). That client is not built. Until it is, a write that must pass an endpoint's own pipeline (its rate limit, its idempotency key, its policy) is a same-origin `fetch` to `/api/v1/…` from the client island, with the key kept across retries of one body. The assistant's dock, its flag button, the suggest form's create and its autosave's `PATCH` do this (recorded in unit 51b and confirmed by Andre on 2026-10-07; the autosave since unit 51c). An island that writes this way refreshes the router after the write (`router.refresh()`, as the dock and the autosave do): the router keeps a page as first loaded for Back and Forward, and only a refresh or a server action clears that, so a page restored from there would show what the server no longer holds (unit 51c's review). An upload's file is `PUT` to the URL its ticket gives, which is the web tier's own route while the store is a directory (unit 51d, part 2; feature-specs/32 § 15). Never a `fetch` to another origin.
- Route files contain no logic. `page.tsx` reads params, calls one loader from `lib/`, renders one screen component. `layout.tsx` composes chrome. `route.ts` calls one handler factory (see API Routes). `loading.tsx` renders a `.loader` string with a number, never a skeleton.
- Route conventions from architecture § 3.2 are fixed: `app/[lang]/…` for every page; parallel slots `@assistant`, `@lab`; the Improve pages are routes of their own (`ch/[n]/improve/new`, `improve/[suggestionId]/…`; feature-specs/34 § 4, the TRD's `@improve` being a notation); intercepting route `(.)ref/[id]` for the peek panel; `app/api/v1/` for REST. Do not create a page outside `[lang]`.
- Content is read at the pinned release only. Every content query passes `releaseId` from `getCurrentRelease()`; cached content uses `unstable_cache` / `"use cache"` keyed by `releaseId` and tagged `release:${id}`, revalidated by tag on publish. Nothing in the app mutates content tables.
- Rendering modes: content pages are static per release; search and account pages are dynamic; the assistant, IDE and suggest form are client components inside a server shell. Mark the intent with `export const dynamic` only where the default is wrong, with a one-line comment saying why.
- Streaming: the assistant uses `ReadableStream` SSE from a route handler with a final JSON event; the client renders citations and "the book does not cover this" only from the final event. The IDE uses one WebSocket per session; no polling.
- Server actions live beside the form that uses them in `actions.ts`, are `"use server"` at the top of the file, validate input with a zod schema as their first line, call OPA second, and return a discriminated union `{ ok: true, data } | { ok: false, error }`. They never throw to the client.
- Metadata: every page exports `generateMetadata` with a title in the form `"21.3 Worked numbers · Chapter 21"` and the `lang` alternate; the `<html lang>` is set from `[lang]`.
- i18n: every user-visible string goes through `next-intl` (`useTranslations` / `getTranslations`) with a key in `messages/en.json` and `messages/pt.json`. No string literal in JSX except ids, versions, hashes, code and glyphs (`✢`, `ƒ`, `·`). A PR that adds an EN key without the PT key fails CI.
- `next/image` for raster only (there is almost none); Mermaid SVG is inlined from the release; fonts through `next/font/google` as ui-context § 13.1 states.
- Environment variables are read once in `lib/env.ts` through a zod schema and exported as a typed object. `process.env` appears nowhere else, with one exception: the variables feature-specs/11 § 8 gives to the gateway and the workers alone (`LITELLM_MASTER_KEY`, `INDIVIDUAL_TOKEN_CAP`, `INDIVIDUAL_TOKENS_PER_MINUTE`) never join the web tier's schema and are read from their own process by `scripts/gateway-stub.ts` and, through `workers/env.ts`, by `workers/main.ts` and `scripts/gateway-key.ts` (units 25b–25d). Two amendments, 2026-10-04: `INDIVIDUAL_TOKEN_CAP` is in `lib/env.ts` as well since unit 35b, because the account page prints the cap on the budget meter (feature-specs/21 § 4.1); it is a number, not a secret, the workers still read their own copy with its tokens per minute, and the two secrets beside it stay out. And `instrumentation.ts` reads `process.env.NEXT_RUNTIME` (unit 35c): the framework's own constant, compared so that the tracer stays out of the edge bundle Next compiles from the same file, and nothing a deployment configures. Client-exposed variables are prefixed `NEXT_PUBLIC_` and contain no secret.
- No `getServerSideProps`, no `pages/`, no API routes outside `app/api/v1/`, no middleware that touches data (`proxy.ts` only rewrites `[lang]` and sets the per-request CSP nonce and header; it reads no cookie and no session, feature-specs/09 D10, 2026-09-22). Security headers: the static set lives in `next.config.ts` `headers()` and the CSP in `lib/security/headers.ts`; the root layout's theme script is the one inline script and carries the nonce.

## React components

- One component per file, named export, file name equals component name in PascalCase (`InstrumentPanel.tsx`). Props type is `interface InstrumentPanelProps` declared above the component in the same file; no `React.FC`.
- Component folders follow architecture § 3.1: `components/chrome/`, `reader/`, `assistant/`, `labs/`, `improve/`, `admin/`. Shared primitives that render a single hb.css class (Chip, StatusMark, EvidenceBadge, Meter, Kbd, Button) live in `components/ui/`. A component used by one feature stays in that feature's folder.
- Components render hb.css classes by name (ui-context § 13.3). A component does not define visual variants with Tailwind utilities; it maps a typed prop to a class (`tier: "PRIMARY"` → `.t-pri`). The mapping object is a `Record<Tier, string>` declared once at module level.
- Props are data, not markup. Pass `figure: Figure`, not `chipClass: string`. Pass `verdict: Verdict`, not `colour`.
- No prop drilling past two levels; no context except `next-intl`, the theme, and the keyboard-map provider. Server data flows down as props from the page.
- Hooks: custom hooks in `lib/hooks/`, prefixed `use`, one per file, only for browser concerns (keyboard map, SSE stream, WebSocket, localStorage with try/catch). No hook wraps a data fetch. A hook that writes on the person's behalf keeps its state in a plain object it makes once, not in refs and callbacks that call each other: `useDraftAutosave` mounts `createDraftAutosave` (unit 51c), which its suite drives with fake timers.
- Accessibility is part of the component contract, not a review item: real `button`/`a`/`input`+`label`; `aria-current` on nav and outline; `aria-pressed` on segments; `aria-label` on icon-only controls; `role="meter"` with values; `role="log"` on conversations; `role="alert"` on errors; `role="dialog" aria-modal` on peek and sheet; `aria-live="polite"` on counters and verdicts. A component missing these fails its Playwright axe test.
- Keys are stable ids from data (`section.id`, `record.seq`), never array indexes.
- Event handlers are named `handle<Event>`; props that receive them are `on<Event>`.
- No inline styles except data-driven widths and grid templates (ui-context § 13.2). No `dangerouslySetInnerHTML` except in `SectionBody` and `MermaidFigure`, which render pipeline-sanitised HTML and SVG from the release and nothing else.

## Styling

- Tokens only. Every colour, font family, font size, line height and spacing value resolves to a custom property defined in `app/globals.css` (ui-context § 2–4). `#`, `rgb(`, `hsl(` and pixel spacing values appear in no other file. CI greps for them.
- Tailwind v4 utilities are used for layout only: `flex`, `grid`, `gap-s*`, `p-s*`, `w-*`, `min-w-0`, `items-*`, `justify-*`. Colour, typography, radius and shadow come from hb.css role classes or token-backed utilities (`bg-bg-2`, `text-ink-3`, `border-rule-strong`, `font-mono`). Never `rounded-*`, `shadow-*`, `bg-gradient-*`, `blur-*`, `truncate`, `line-clamp-*`, `transition-*`, `animate-*` (except the one caret blink defined in globals.css).
- Component classes are the hb.css names, ported into `@layer components` in `globals.css`, unprefixed. Add a variant by editing `globals.css` and `context/ui-context.md` in the same PR; never by composing utilities in a component.
- Radius is 0 and elevation is none. The only `box-shadow` values are the hard inset bars and underlines listed in ui-context § 4.4.
- Class order in JSX: hb.css role classes first, then layout utilities, then `data-*`/state classes. Use `clsx` for conditional classes; never string concatenation.
- Dark theme is token-driven through `data-theme` on `<html>` and `prefers-color-scheme`; components never branch on theme.
- Nothing truncates. Text wraps; only `.hash` and ids use `overflow-wrap: anywhere`. Widths are sized to the longer of the EN and PT strings.
- Motion: none except the running caret. Under `prefers-reduced-motion: reduce` everything is static.
- Icons: none. Glyphs and inline stroke SVG only, per ui-context § 13.4.

## API Routes

All endpoints live under `app/api/v1/` and follow architecture § 3.4.

- One `route.ts` per resource path exporting only the HTTP methods it implements. Each method is `export const GET = handler(spec)` built by the factory in `lib/api/handler.ts`, with the spec in `lib/api/endpoints/*.ts` (registered in `lib/api/endpoints/index.ts`, from which `npm run api:openapi` writes `openapi.json`). The pipeline runs in this fixed order (built 2026-09-22, feature-specs/09 § 7): trace id → parse params, query and body with the endpoint's zod schemas → resolve session (cookie or bearer) and the role gate → same-origin check on cookie mutations, and on a GET whose spec says it writes (`writes: true`: an export, which appends its own record; such a GET also refuses HEAD, which Next answers with the GET's handler; since the 52c review) → rate limit → `Idempotency-Key` where the spec requires it → call OPA with `{subject, action, resource, context}` → run the endpoint function inside the tenant context → serialise the response with the response schema → emit the span. A handler cannot skip a step; the factory has no opt-out flags.
- Validate before anything runs. The endpoint function receives typed `{ params, query, body, session }` and never sees the `Request`. Invalid input returns 400 or 422 with the failing field named.
- Enforce authorisation and ownership before any read or mutation. The OPA input names the concrete resource (`suggestion:S-15-0377`, `lab-session:…`, `org:…`); ownership checks are policy rules, not `if` statements in handlers. OPA unreachable is a 403.
- The policy's subject is made of the session and of nothing else: `subjectOf(session)` (feature-specs/29 § 14). A session user carries `identityVerified` and, for a curator, the roster's `parts`; code that builds one by hand (a fixture, a synthetic account) states both, as the least they could be. A resource names what its rules read (`ownerId`, and for a suggestion `parts`, `changeClass`, `origin`): a rule that reads a field the caller left out does not fire, so leaving one out refuses. The OPA sidecar serves the bundle it was started with: after a change under `policies/`, run `opa test policies` and restart the sidecar; `tests/integration/improve-policy.test.ts` says so when it meets an old one.
- An account's role and its verification are the identity provider's. The application writes them in `lib/auth/link.ts` and nowhere else: the mirror at sign-in, and `resolveDevUser`, which gives them only where the development provider is on and refuses elsewhere (feature-specs/29 § 15). `devProviderEnabled()` is `lib/auth/devProvider.ts`; a new use of it is a new door out of production's rules and is argued in a spec first.
- Response shapes are fixed and typed by the schema that generates the OpenAPI document. Success: the schema object, or `{ items, count, ms }` for lists. Error, everywhere: `{ code, message, detail?, traceId }` with a declarative message that names the fix, in the user's language. No other shape ever leaves a handler.
- Status codes follow the catalogue: 400 malformed, 401 no session, 402 budget or IDE-minutes cap, 403 policy deny or wrong part, 404 not found, 409 conflict (already running, no seats, duplicate flag), 413 file over 1 MB, 422 semantic failure (no anchor, rationale > 200 words, intake sensor named, region not offered), 429 rate limit or throttle, 503 pool empty. A refusal by the assistant is a 200 with a `refusal` field, not an error.
- Mutations that the spec marks idempotent honour the `Idempotency-Key` header by returning the stored first response; the key is scoped to user and path. A spec whose response body is a stream marks it `idempotent: "endpoint"` (the assistant's ask endpoint, feature-specs/15 § 5.3): the pipeline still requires the key, claims it, and refuses an in-flight duplicate or a mismatched body, and hands the endpoint the claim, because a stream's outcome is not known when the handler returns and a replay has to answer in the same medium. No step is skipped; the factory still has no opt-out.
- Long work never runs in a handler. Anything over a few hundred milliseconds starts or signals a Temporal workflow and returns `{ id, state }` or `{ workflowId }`; the client observes progress over SSE, WebSocket or a subsequent GET.
- Handlers do not write ledger records, budget rows or calibration data for workflow-owned events. They start or signal the workflow, and the workflow writes.
- Handlers never call the gateway, never hold a provider or virtual key, and never serialise a header, env var or config object into anything a model reads.
- Webhooks (`/webhooks/ci`, `/webhooks/temporal`) verify the HMAC signature or mTLS identity before parsing the body, are idempotent by delivery id or event id, and return 204 on duplicate delivery.
- Public endpoints are listed explicitly in the handler spec (`auth: "public"`); the default is `auth: "session"`.
- Every endpoint has a contract test in `tests/contract/` that asserts the request and response against the OpenAPI schema, the error body shape, and the rate-limit headers.

## Data and Storage

- PostgreSQL holds metadata, relations, state and the search index; object storage holds files; the Next.js data cache holds rendered content per release; the URL holds view state; `localStorage` holds per-viewer conveniences only (architecture § 4.1 is the authority).
- Large or binary content never goes in a database column: evidence uploads, saved lab files, run logs, audit packs and lab images live in object storage and the row keeps a `storageKey` and a `sha256`. Object storage is reached through `lib/storage/` only (unit 49b): `putObject`, `getObject`, `headObject`, `signedPutUrl`, `signedGetUrl`; a key is built by the helpers of `lib/schemas/storage.ts` (`evidenceSourceKey`, `evidenceTextKey`) and never from a person's text; the store is a directory for now (`OBJECT_STORE_DIR`) and a bucket later, behind the same interface. A file reaches a browser through a signed URL and no other way; the storage routes (`lib/api/endpoints/storage.ts`) verify the token before the policy is asked and read no session. What a model grades is never an object a person can still write (unit 49f): a signed PUT URL accepts PUTs until it expires, so the grader's activity copies what it checked under a key only it writes (the item's `text` key) and refuses an upload whose sha256 is not the one recorded when it was opened (a link's source only that activity writes). A text column over a few kilobytes (rationale, curator note, message text) is allowed only where the schema already defines it, and the ledger stores its hash, not the text.
- A position the pipeline reports (`ChapterPositions`, feature-specs/33 § 4.1) is never a guess: where the file does not hold a row's text as one run, it is null with its reason, and nothing locates an anchor by searching the file for its words. Positions sit beside the rows and never in them: a field added to a row, a section or a figure changes every chapter's content hash.
- Content rows are immutable. Code never issues `UPDATE` or `DELETE` against `Release`, `ChapterVersion`, `Section`, `Figure`, `SourceRow`, `DeriveLink`, `Lab` or `LabFile`; the content pipeline only inserts. The Prisma client extension rejects such writes outside `pipeline/`, with the one exemption architecture § 11 invariant 3 names (feature-specs/12 § 4.2, D3; recorded here review round 2, 2026-09-24): the embedding job's `Section.embedding`, `embeddingModel` and `embeddedAt` under `EMBED=1`, three columns the book does not contain and `renderHash` does not cover. `contentWriteAllowed` in `lib/db/client.ts` admits that one `update`/`updateMany` for Prisma, and `requireEmbedWrites` in `lib/db/search.ts` guards the raw statement that writes the vector, because raw SQL does not pass the extension at all.
- The ledger is append-only. `LedgerRecord` is written only through `lib/ledger/append()`, which canonicalises (RFC 8785), hashes (SHA-256), links `prevHash` and inserts in one transaction with a `SELECT … FOR UPDATE` on the chain head. No other code path inserts into the table. A kind's payload is a strict schema in `lib/schemas/ledger.ts`, and since unit 46c (feature-specs/29 § 13) a new payload, or a new member of one, is held to two things by `lib/schemas/ledger.test.ts` without a line being added: no string in it accepts a sentence (text a person or a model wrote is its sha256, and anything else has a form), and no key rides in that the schema does not name. A new kind also states in `recordIssue` who may be its actor and whether its record names a suggestion.
- Every account-scoped query goes through the Prisma client from `lib/db/client.ts`, which applies the `organisationId` filter. Raw SQL (`$queryRaw`, `$executeRaw`) is allowed only where `lib/db/RAW_SQL.md` lists the statement with its reason and its tenant argument, and each one is reviewed for tenant scoping (the register is the authority, so this list cannot go stale on its own; rewritten review round 2, 2026-09-24). Today that is `lib/search/hybrid.ts` (the one search statement), `lib/db/search.ts` (`embedReleaseStatus`, `sectionsToEmbed`, `writeSectionEmbeddings`: `Section.embedding` is `Unsupported("vector(1024)")`, so Prisma can neither select, filter nor set it — feature-specs/12 § 4.2, D3, the write guarded by `requireEmbedWrites` under `EMBED=1`), `lib/api/ratelimit.ts` (the atomic token bucket), the ledger's head lock and `setval` (`lib/db/ledger.ts`, `lib/ledger/append.ts`, which Prisma cannot express), the migrations, and the two read-only test statements (`tests/integration/search.test.ts`, `tests/integration/ledger.test.ts`). `lib/rubric/score.ts` is not written yet and needs none of it when it is: score arithmetic is pure.
- Queries live in `lib/db/<domain>.ts` as named functions that take typed arguments and return DTOs; components and handlers never call `prisma.*` directly. One query per chapter load (`ChapterVersion` with sections, figures, source rows); no N+1.
- Migrations are forward-only, one per PR, additive; a column is removed only in the release after the code stopped reading it. A correction to an applied migration is a new migration, never an edit. A `NOT NULL` column with no default is added in three statements — add nullable, fill or fail loudly on the rows that exist, then `SET NOT NULL` — because a one-statement add fails on any populated table; the one-statement form is allowed only where the table is provably empty and the migration says so. A foreign key whose table carries a `CHECK` over the same column names its `ON DELETE` action explicitly: Prisma's default for an optional relation is `SET NULL`, which such a `CHECK` then refuses (decided 2026-09-23, unit 25). Seed data is the fixture release (chapters 21, 28, 37), rubric v1.2 and the four PRD worked examples, in `prisma/seed.ts`.
- Money, tokens and sequence numbers are `BigInt`/`bigint`, and so is a duration in milliseconds that a wait can stretch: an `Int` holds 24 days and 20 hours of them (`CuratorAction.queueWaitMs`, unit 53's review), and the door reads it back as a number; scores and counts are `Int`; multipliers and figure values are `Decimal`, never `Float`. One exception, decided 2026-09-24 (unit 38): the ledger's `seq` is `Int`, because it is a member of the record's hashed form, which is RFC 8785 canonical JSON and has one number type with no exact representation beyond 2^53; a `bigint` would have to be hashed as a string, changing every hash in the chain to buy a range no ledger will reach.
- Secrets come from the vault into `lib/env.ts` at boot; nothing reads them later, nothing logs them, and the secret scanner in CI checks prompt templates and logged prompts for a zero count.
- Retention jobs (30-day message-text purge, 30-day account hard delete) are Temporal schedules in `workers/` from Phase 4, when Temporal arrives (project-overview § In scope: Phases 2 and 3 do not need the workflow engine). Until then they are `scripts/*.ts` run on a schedule, like `npm run auth:sweep`, and each run writes its ledger record itself (decided 2026-09-23).
- The improvement tables (feature-specs/29 § 3, § 11; unit 46a) are the platform's: no tenant column, and no module but `lib/db/improve.ts` names them, through the client or in SQL (`tests/improve-door.test.ts` and a CI step search for it). A function of that door takes its caller first and writes the condition that makes a row the caller's into the query; it takes the client it runs on last, so it can join a transaction; it returns to a service no column that names a person; and it reads a suggestion one statement at a time, never one query with several relations, which the client would run as several statements at once on a transaction's connection (feature-specs/29 § 12). A unit that needs another query on these tables adds a function there. Three rules a later migration to them keeps. A row that names a person does it with a nullable column and `ON DELETE SET NULL` (or is the person's own and cascades), so that an account's hard delete is never refused. A row that names content does it by id or anchor with no foreign key, as `Conversation` and `Citation` do. And a child of `Suggestion` cascades from it, because the one refusal that matters is at the suggestion: the database deletes a suggestion only while it is a `DRAFT`. A test of what the database itself must refuse asks the database, in SQL, inside a transaction that is rolled back, and is listed in `lib/db/RAW_SQL.md` (`tests/integration/improve-schema.test.ts` is the pattern).

## Workers, workflows and agents

- Temporal workflows in `workers/workflows/` are deterministic: no I/O, no `Date.now()`, no random, no direct database access. All side effects are activities in `workers/activities/`, each idempotent and keyed (`suggestionId`, `runId`, `seq`). A wait until an instant is measured by the activity that learns of it, and the workflow sleeps that long (unit 50f: a budget cap's reset).
- A worker that needs the pipeline's ingestion or the embedding job runs it as its own process through `pipeline/publish.ts` (node with tsx's loader, from the application's folder, `PIPELINE=1` or `EMBED=1` set for that process alone), never by importing it or setting either flag in the worker's own environment (since unit 54c; architecture § 11 invariant 3). Its exit code is the answer (the ingestion's 2 a render hash that differs, 3 a release that is another's), and the row says its last line.
- A workflow starts another as its child with `executeChild` under the child's own id (`merge:<id>`, since unit 54b), and catches the child's failure where the parent must go on. The child's activities are registered with every other, and a suite that runs the parent registers doubles of them too.
- A workflow that waits with no timer — `SuggestionWorkflow` since unit 50e — replays its code whenever the workers restart: a change to what it asks of the engine (an activity, its order, a timer) is made with `patched()`, or the development engine's waiting runs are ended before the workers restart on it. Such a run keeps every signal, whenever it comes, and leaves it to the signal's activity to judge whether it still applies; a test asks its query what it waits for. A change made with `patched()` ships with a replay test of a history recorded on the code before it (`tests/fixtures/workflows/`, the History message's protobuf encoding: this install's copies of protobufjs break the SDK's JSON helpers), and the `patched()` check sits at the one new command, never at a handler or a condition (a check at the start answers false while a waiting run replays, and is not remembered). Before the workers restart on such a change, the development engine's running histories of that workflow are replayed against the new bundle (`Worker.runReplayHistories`; feature-specs/45 § 17).
- One workflow file per workflow (`SuggestionWorkflow.ts`, `MergeWorkflow.ts`, `AnswerWorkflow.ts`, `ExportWorkflow.ts`); one activity file per concern (`sensors.ts`, `grader.ts`, `adjudicator.ts`, `ledger.ts`, `git.ts`, `throttle.ts`). Activity input and output types are zod schemas in `lib/schemas/workflows.ts`.
- Agent prompts are assembled only in `workers/agents/<agent>/assemble.ts` in the fixed prefix order from architecture § 6.1, from the versioned guide file and the fields the agent may read. The function's parameter type lists exactly those fields; a contributor name, employer, other suggestion or curator note cannot be passed because the type has no place for it. The evidence grader (unit 49d) is `workers/agents/grader/assemble.ts` `assembleEvidenceGrader`, whose `EvidenceGraderInput` has the guide, the rubric, the anchor, the change and the document and nothing else; a PDF or an image (49f) enters as the provider's `document` or `image` block between the fence's opening and closing text blocks, base64 and never a URL source, which would have the provider open a stranger's URL (invariant 34), and is checked against the provider's documented limits (`lib/improve/media.ts`) before it is sent; `grade.ts` in the same folder is the assistant's grounding grader of spec 13, a different agent with its own input type. Independence is `lib/improve/independence.ts` `stakeOf`, called by `evidence.ts` after the model has answered and never by an assembler.
- Model outputs are parsed with the agent's zod output schema; a parse failure is the agent's one cap (assistant: repair once; grader: tier U with reason; adjudicator: curator queue). Nothing numeric is read from the output: scores, thresholds and decisions are recomputed by `lib/rubric/`.
- Fetched evidence and tool output enter a prompt as fenced, labelled untrusted data and never as instructions; the fence is applied by `assemble.ts`, not by the caller.
- A request never carries `tools`: `callModel` refuses one (`GATEWAY_TOOLS_REFUSED`). The provider's web search and web fetch, the only tools the product knows, go on `GatewayCall.serverTools` (`ServerToolsSchema`, since unit 58a; feature-specs/41 § 3), and a turn that may be paused runs through `lib/gateway/turn.ts` `callModelTurn`, one ledger row a request. What came back besides the text is read with `lib/gateway/tools.ts`, by shape.
- Every model call goes through `lib/gateway/client.ts` `callModel` with the principal's virtual key read from `GatewayKey` and decrypted under `GATEWAY_KEY_SECRET` (workers only), logs guide version, pinned model id and prompt hash, and raises the gateway's budget refusal as a typed `BudgetExceededError`; the caller passes a `GatewayCall` (`lib/schemas/gateway.ts`) and a request built from `lib/gateway/policy.ts` `requestFor`. Where a purpose and alias have two rows (since unit 49f, the evidence grader's for a text and for a PDF or an image) the call names its row (`GatewayCall.row`). A request that carries a provider's document or image is bounded before the call as the proxy will send it (`requestBytesBound`: the base64 as it is, the rest three times and U+007F six, for the proxy's `json.dumps`), since the gateway sets no request-size limit of its own.
- The web tier reaches the workers only through `lib/workers/client.ts` `workersFetch` (feature-specs/11 § 7.2): the body is a typed row of `lib/schemas/workers.ts`, validated again by the workers; the bearer `WORKERS_TOKEN` and the `traceparent` are added there; a connection failure or a timeout is `WorkersUnavailableError` (503) and the workers' error body `WorkersRefusedError` with its code. The schemas are `lib/schemas/workflows.ts`, built without a bare `z.string()`, and `freeTextIn` (`lib/schemas/freeText.ts`) walks everything that file exports in its test: a string there is a uuid, an instant or a pattern that refuses a sentence, and a kind of schema the walk does not know is a finding (feature-specs/28 § 5.3, § 14; architecture invariant 35).

A workflow is an entry of the `WORKFLOWS` table in `lib/schemas/workflows.ts` (its task queue, the schema of its id, its argument, its result, its signals and its queries), added in the unit that writes the workflow; the client validates against it before it sends. Every call is held to one deadline by the client itself and fails closed: `WorkflowsUnavailableError` is a 503, and `WorkflowNotFoundError` says the engine answered and nothing runs under that id. A handler writes the state that says "started" only after the start returned, and says in its own words what was not done. No other file of the web tier imports a package of the SDK, and that one imports `@temporalio/client` alone; lint holds both.

A model-call activity sets no retry of its own, because the gateway client already retries by its request row and every agent's cap is one attempt.

- The researcher's two assemblers are `workers/agents/researcher/planner.ts` and `reader.ts` (since unit 58; feature-specs/41 § 5, § 6) and share only `render.ts`, which renders the book's side — a section with its figures and rows, a fence — and never a turn's text: what the reader is given is typed, and the type has no field for a question, an answer, the uncovered sentences or a user. The reader's findings pass `lib/research/validate.ts` before they become anything, and a source is only an `https` address the call's own tool results showed. ## Testing

- Every pure module in `lib/` has a Vitest unit test beside it (`score.test.ts`). `lib/rubric/` and `lib/ledger/` require 100% branch coverage and include the four PRD worked examples as fixtures with their documented outcomes.
- Every endpoint has a contract test; every Rego rule has an OPA test for its deny cases including cross-tenant and the agent identity; every workflow has a suite in `tests/workflows/` that runs its real code, bundled as the workers bundle it, on Temporal's time-skipping test server with its activities replaced by doubles (`workflowEnvironment()` of `tests/workflows/environment.ts`; feature-specs/28 § 6, § 13). Those suites are part of `npm test` and need no container: a wait of days takes milliseconds. Their tests run one after another, never `concurrent`, because the server has one clock; a workflow whose children outlive it (a child abandoned at its parent's close) is awaited with the environment's `resultOf`, which moves the clock one step at a time, never with `handle.result()`, which leaves the clock free to run into the ten-year execution timeout the test server gives every workflow (unit 59, 2026-10-10); a server that cannot start fails the suite naming `npm run workflows:test-server`, and never skips. What an activity does is tested beside it, or against the database; that the pieces meet on the real engine is `tests/integration/workflows.test.ts`, which runs where `DATABASE_URL` and `TEMPORAL_ADDRESS` are both set.
- Every screen has a Playwright test of its primary flow in EN and PT that runs axe (zero AA violations) and a PT-truncation snapshot at 390px and 1440px. The truncation suite is `tests/layout/pt-truncation.spec.ts` (`npm run test:layout`, unit 23c): a screen is added to its list, and its snapshot is of the layout's facts (per screen and width, the labels measured and each one truncated, written to `pipeline/reports/`), not of pixels, in keeping with the next rule. The flows with axe are `tests/e2e/` (`npm run test:e2e`, unit 23d): a flow is written once with `defineFlow` and runs in EN and PT, finds its controls by role and by the catalogue's own words for that language (a class only where a control has no words), takes its chapter from Book Home and its sections from the outline instead of naming content, scans each screen it reaches with axe, and leaves the account of the suite's own reader (`e2e-reader@harness-bible.local`) as it found it. Beside the flows the suite walks every reader page with the keyboard, clicks every cross-reference, and resumes each reading path in a second browser context; each test writes its part whether it passed or not and the run's teardown gathers them into `pipeline/reports/e2e-<release>.json`, which the Phase 1 gate reads. No browser suite asks the assistant a question that reaches a model: a suite anyone may run spends nothing.
- A browser suite signs in as one of the suite's own accounts, never a person's: `READER`, `CONTRIBUTOR`, `CURATOR` in `tests/e2e/support.ts`, through `signIn` or, for a session kept across tests, `accountSession` (unit 46e). A suite that needs a curator of a part sets the roster itself with `npm run roster:set` and says so.
- Tests use the fixture release and named ids from the specs (`S-15-0377`, `21.3`, `F-23-06`); no `foo`, no random data, no snapshot of a whole page.
- A test that mocks the database, the gateway or Temporal is a unit test and lives beside its module (`lib/`, `workers/`, `pipeline/`); anything else uses the real dependency in a container. The fetcher's suite (`workers/fetch/fetch.test.ts`) is the one exception in kind: it runs the fetcher's own transport on `node:http` against a server of its own on the loopback, with a resolver double giving public addresses to the suite's names, so that `npm test` reaches no network; what the real transport adds, TLS to the pinned address, is checked by hand with `npm run fetch:check`. `tests/` holds the contract, integration and e2e suites, the workflow suites (`tests/workflows/`, on the test server) and the ones that read the repository itself (the lint rule, the gateway's configuration files, message parity). `tests/fixtures/improve/` (unit 50g) holds the four worked examples and the harness that runs them end to end — the workers' own activities on the stub gateway started in the process and a fetcher given the fixture's documents — for their suite and the development seed (`scripts/improve-seed.ts`, which imports it as `scripts/workflows-test-server.ts` imports `tests/workflows/server.ts`: a script of development, never of the product); like `tests/workflows/`, it may import the workers.

## Git and review

- Conventional commit subjects, imperative, under 72 characters, scoped by folder: `feat(reader): peek panel for cross-references`, `fix(rubric): corroboration added once`. Body says why and names the spec section it implements.
- One concern per PR. A PR that touches `globals.css` also touches `context/ui-context.md`; one that touches `lib/schemas/api/` regenerates the OpenAPI document and the client; one that touches `prisma/schema.prisma` includes exactly one migration.
- CI gates on every PR: `tsc --noEmit`, ESLint with zero warnings, Vitest, OPA tests, contract tests, the token grep (no hex outside `globals.css`), the message-key parity check, and the PT truncation snapshots. Integration, e2e, lab suite and load run on merge to `main`.
- No force pushes to `main`; no skipping hooks; no merging with a red check.
