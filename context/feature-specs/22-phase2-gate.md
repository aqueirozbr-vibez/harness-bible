## 1. Purpose

The gate turns the seven promises of Phase 2 into measurements a reviewer can rerun. Like Phase 1's, it measures against the running system and the real rows, writes one report, and refuses to say "met" unless every criterion passes on its own evidence. Criteria that need something the repository does not hold, such as curator labels or a provider key, come out `blocked` naming the missing thing, so the report is also the list of what remains.

**As built (36a, 2026-10-04).** `lib/gate/common.ts` holds what both phases share (`Criterion`, `GateReportBase`, `gateVerdict`, the nearest-rank `percentile`, `formatGateReport`, which now prints `Phase {n} gate`); `lib/gate/phase1.ts` re-exports them and keeps `bareNumbers`, so `scripts/phase1-gate.ts` and its tests are untouched. `lib/gate/phase2.ts` is pure and has one builder per criterion: four read run files and labels (`citationCriterion`, `kappaCriterion`, `latencyCriterion`, `prefixCriterion`), six take a small record of facts the script will measure in 36c (`RefusalCheck[]`, `SubstitutionCheck`, `WalkCheck`, `FlagCheck`, `RetentionCheck`, `LedgerCheck`) or `{ blocked }` / `{ deferred }` with the reason, which is never a pass. Decided where the table left room:

- **P2.1a** counts an answer when it is an answer, no claim was unfound and none was replaced; a non-refusal item that was refused or failed is in the denominator and not in the count. A run that stopped early fails whatever its rate so far (§ 7). Without a real run it is `blocked`, with the stub's counts in the note as shape only.
- **P2.1b** pairs a label with the answer it names by `messageId`, and only when that answer was graded; labels that match nothing are counted in the note. `cohenKappa` returns 1 when the two readers agree on every pair, the one case where the formula has no value. Its test uses the book's own worked example (chapter 12: agreement 0.85, chance 0.53, κ 0.68).
- **P2.5a** is the nearest-rank p95, as Phase 1's gate computes a percentile, over the run's answered items. The dashboard's series (21 § 5.3) interpolates (`percentile_cont`), so this row's "the same number" holds only when the 95th rank falls on a sample; the two can differ by less than the gap between two neighbouring samples. The gate's number is the one this section defines and its note says `nearest rank`.
- **P2.5b** has two halves, both required. The prefix is **one for the whole run** (corrected in 36b): the single cache breakpoint sits immediately after the guide (`workers/agents/assistant/assemble.ts`), so the cached prefix is the guide's bytes whatever the mode, and its hash is the row's `guideSha256`. The release line, the mode's line, the sections and the question all come after the breakpoint. 36a had compared the prefix per mode and read the row's `promptSha256`; that hash also covers the retrieved sections, so it differs with every question (201 distinct values over the stub run's explain answers) and could never have been stable. The cache is read **call by call** (`cacheVisible`): the first frontier call of each kind, the draft's and the grader's, writes its prefix and reads nothing, and every later call must read some; a run with no later call shows nothing and fails.
- **P2.2** requires a pointer for `R-SCOPE-OT` and `R-RECOMPUTE` as the row says, counts calls on the small alias and reports them without failing on them, and fails a cause that was never asked.

**The script as built (36c-1, 2026-10-04; `scripts/phase2-gate.ts`, `npm run gate:phase2`).** Unit 36c is split in two, because it touches two areas: the report and what is read from files and from the ledger (36c-1), and the gate's own turns through the API (36c-2). 36c-1 measures P2.1a, P2.1b, P2.5a and P2.5b from the run files and the labels, and P2.7 from the ledger; P2.2, P2.3, P2.4, P2.6a and P2.6b are `deferred` and name 36c-2. `phase2Criteria` lists the ten in the overview's order and `phase2Report` assembles the report, both pure (`lib/gate/phase2.ts`). Decided:

- **The gate never pays.** It reads what `npm run gate:golden` left behind. P2.1a, P2.5a and P2.5b are `blocked` until a **whole** real run exists, and their note says what to run; "a provider key" alone, the wording of 36a, is not what they wait for.
- **A pilot is not a run.** `--limit` writes `golden-run-<release>-pilot-<grade>…jsonl`, which `newestRun` does not match, so five paid items are never read as the golden set and a stub pilot never replaces the stub run (nor its rows). A real run that the budget stopped is still read, and still fails P2.1a (§ 7); P2.5a and P2.5b then say in their note that the run stopped early.
- **P2.7** checks every answer of the run the report read (the real run, else the stub's) against the record at its `ledgerSeq`: an `ANSWER` record that reads under the payload's own schema, names that answer's message, is not a refusal's, has verdicts, and holds citations whenever the answer cited (`answerRecordComplete`). The chain is verified from genesis to its head in memory, which a development chain allows. On a stub run it is measured and can pass: the records are the product's own, whichever gateway answered.
- **Found while reading for 36c-2** (settled in 36c-2 and 36c-3, below). (a) This table's P2.3 says no `token` event may hold the uncited claim's own text. The stream as built sends the draft's words as they arrive and replaces them on `final` (architecture § 6.4; spec 16 § 5.4: the pending text is plain, `aria-hidden`, and never kept beside the answer), so that half of the measure fails by design. The overview's criterion is that the **substitution** is visible only after `final`; 36c-2 will measure that, report whether the claim's words streamed, and not fail on it unless Andre decides the stricter reading (tracker, Open Questions). (b) P2.4's walk is on chapter 37, which release 2026.09 has not verified: the walk refuses as `R-UNVERIFIED` before its script runs (the stream suite pins this), so P2.4 will be `blocked` on the book's side, with a walk on a verified chapter as shape only. (c) There is no `uncited` fixture in the stub yet; 36c-2 adds the switch.

**The gate's own turns as built (36c-2, 2026-10-04; `lib/gate/api.ts`, `lib/gate/measure.ts`, `workers/gate/stubStack.ts`).** 36c-2 measures P2.2 and P2.3. It grew past one sub-unit, so the flag and the purge (P2.6a, P2.6b) are 36c-3 and the walk (P2.4) is 36c-4. Decided:

- **"Through the API" is the endpoints, in the gate's own process.** `startGateApi` signs a reader in (`gate-check@harness-bible.local`, a development account of its own) and calls the functions the routes serve, `conversationCreate` and `askEndpoint`, with that reader's cookie, so every turn passes the whole pipeline: session, origin, rate limit, idempotency, policy, the endpoint, the stream. The workers it is pointed at are the stub stack of 36b, started in the same process. This is how the stream suite asks, and it is why the gate does not need the development server, the workers or a gateway to be running: three of its checks need an answer made to order, which only the stub gives, and a gate must be rerunnable without paying. It does need the database and the policy sidecar (§ 7).
- **The trace id is the gate's.** It sends a `traceparent`, the pipeline keeps it, and the turn's gateway calls are found by it in the stack's memory. That is how "zero frontier calls" is read without a row in `BudgetLedger`.
- **P2.2** asks one golden question per cause, each in a conversation of its own in the context its item names: `R-UNVERIFIED` from a chapter the release has not verified, the other three from one it has (`pickRefusalItems`), because an unverified chapter refuses for its own cause first. `refusalCheckOf` reads the `final` event (`refusal.cause`, `code`, `pointers`, `beforeRetrieval`), counts the turn's calls on the frontier and the small alias, and verifies the record `final` names: an `ANSWER` record of that message, a refusal for that cause, whose stored hash is the hash of its own fields and the one `final` carried. The classifier's cause is the stub's to be told (its header switch); the three rule causes are the flow's own.
- **P2.3 measures the overview's criterion, and reports the rest.** The stub gained a switch, `x-hb-stub-claim: uncited`: one more claim, citing the first retrieved section and sharing no word with any section, which the citation sensor replaces (13 D5). `substitutionCheckOf` joins every `token` event's text, because a sentence can straddle two deltas, and reads the `final` claims and the stored text. It fails when the substitution sentence appears before `final`, when `final` marks nothing as substituted or still carries the claim, or when the stored text lacks the sentence or keeps the claim. It does **not** fail when the claim's own words streamed: the stream is the draft as it is written and the client replaces it on `final` (architecture § 6.4; spec 16 § 5.4), so this row's "and of the uncited claim's text" is not what was built. The note says whether they streamed. They do.
- **A request the pipeline refuses stops the gate.** A 403, a 429 or a 400 before any stream is not a measurement of the assistant; the gate ends with what the API answered and writes no report.
- **What a gate run leaves:** five conversations of the gate's account, replaced by the next run, and five `ANSWER` records in the chain, which stay.

**The flag and the purge as built (36c-3, 2026-10-04; `lib/db/calibration.ts`, `lib/gate/measure.ts`, `lib/db/assistant.ts`).** 36c-3 measures P2.6a and P2.6b. The rest of 36c is two areas, the stored rows and the decision aids, so the walk (P2.4) is 36c-4 and is `deferred` until then. Decided:

- **The calibration set exists now, as the query 17 § 4 says it is.** `calibrationSet()` returns every flagged message with its mode, the flag's kind, coded reason and time, the refusal cause when it is a refusal, `grounded`, the verdicts, the citations, the guide version and the model id. A row holds no text and nothing that says who flagged it: it calibrates a grader, and the flag outlives the words it was about. The flags are every reader's, so one registered statement names the readers who have a flag and each reader's rows are read inside that reader's own tenant context, the purge's shape (`lib/db/RAW_SQL.md`); the guard's exemption is not widened.
- **P2.6a** asks an ordinary golden question, flags its answer through `POST /api/v1/assistant/messages/{id}/flag` with the coded reason `wrong_citation`, and looks the answer up in the set. `flagCheckOf` wants the row to carry as many verdicts as `final` did (and at least one), the score `final` had, and the reason the flag gave. The score of a stub answer is none, because the stub's grader gives no verdict; the row carrying none is the row agreeing with the answer, and the note says so instead of failing.
- **P2.6b runs the product's own purge with its clock 31 days ahead, for one reader.** `purgeAssistantText` gained `reader`: the nightly job never sets it, the gate sets it to its own account. This replaces the row's "on a copy of the run's conversation": a clock moved ahead for every reader would take every reader's words early, the demonstration's among them, and a copy would not be the row the flag is on. It is watched on the answer P2.6a flagged. `retentionCheckOf` compares the conversation before and after: the words were there and are gone from every message, every citation's quoted claim is gone, `textPurgedAt` went from unset to set, the citations and verdicts are counted again only when each is still what it was (the quoted claim aside), and the answer's ledger record has the same hash and the same payload in canonical form. A purge that did nothing, or a conversation that had no words to lose, passes nothing.
- **The gate's reader is a reader like any other.** Its turns, its flag and its purged conversations are in the series of spec 21 and in the calibration set, as a reader's would be; against a database of real readers the gate would add six turns and one flag a run to both. It is a development and staging tool until someone decides otherwise.
- **What a gate run leaves now:** six conversations of the gate's account, their words taken by its own purge, replaced by the next run; six `ANSWER` records in the chain; one flag, removed with its conversation by the next run.

**The walk as built (36c-4, 2026-10-04; `lib/gate/walk.ts`, `lib/gate/measure.ts` `measureWalk`).** 36c-4 measures P2.4, and with it no criterion is `deferred` any more. Decided:

- **The walk is asked as the dock asks it.** One turn through the API in mode `walk`, with the aid's id, its inputs at the aid's own defaults (which are the book's P-101 inputs), the dock's own line in place of a question (`assistant.walk.userLine`) and the aid's section as context.
- **"The chapter's own figure" is checked against the release, not against the product.** The expected headline is computed in the gate from `Lab.derived`, the run the pipeline ingested with the release (for 37.8: `A/total` over `C/total`, 810 over 237.6, to one decimal, 3.4×), and every value every step reads is compared with that run, numbers within floating-point noise. The product's presenter is not asked: a gate that asked it would compare the product with itself. The line is the one the aid's step declares (24), the price date is the turn's `pricesVerifiedAt`, and the derive sensor must have matched every explanation (`derive output matched · n of n`).
- **Two things block it, and both are outside this repository.** A chapter the release has not verified: the walk refuses as `R-UNVERIFIED` before its script runs, as any question about that chapter does, and verifying a chapter is the book's side. And a container runtime that does not answer when the script runs in a container (`AID_RUNNER=docker`, the default): the gate asks `docker version` only after a script failed, and blocks on Docker only then. Any other refusal or failure is the product's and **fails**: a refusal of a verified chapter, a script that exits non-zero with Docker up, a turn that ends without a result.
- **Beside a blocked walk, another aid is walked as shape only.** The first aid of a verified chapter (21.8 today) goes through the same check, and its sentence is in the note: exit code, its headline against the release's run, the line, the derive verdict, whether the values are the release's. It is not held to a price date, because an aid need not have a priced step, and it changes no status.
- **On release 2026.09 the criterion reads `blocked`.** Chapter 37 is one of the seven the release has not verified. The 21.8 walk beside it ran in the container: `exit 0 · 76.9%, which is what the release's run gives · ƒ L8 · derive output matched · 4 of 4 · values equal the release's run`.
- **The suite runs the script under the local interpreter** (`startStubStack({ aid: { runner: "python" } })`), as the stream suite does; `npm run gate:phase2` uses the environment's runner. A gate run now leaves eight conversations of its account and eight `ANSWER` records.

## 4. The golden run as a measure (`lib/gate/goldenRun.ts`, 36b)

Runs every golden item through the workers' `/answer` route (the same path the API uses, minus the web tier), one conversation per item, in the item's `context` and `mode`, at concurrency 2 against the real gateway (the rate limit is 20 a minute per user; the run uses a gate principal with its own virtual key and a `hb-gate` purpose label on `BudgetLedger` rows so the spend is attributable and excluded from the account meter's consumer rows) and 8 against the stub. Per item it records `{ id, kind, mode, outcome, citedSections, citedFigures, expectedHit, substituted, verdicts, grounded, firstTokenMs, totalMs, frontierCalls, smallCalls, cacheRead, ledgerSeq }` into `pipeline/reports/golden-run-<release>-<stub|real>.jsonl`. `expectedHit` is true when every `expected.citations` entry is cited (for compare, every `expected.chapters`; for refusal, the cause matches). Cost: 300 items × (draft + grader) on `hb-frontier` is reported at the end from the ledger rows (an estimate before the run from `prices.ts` and the golden set's sizes is printed and the script asks for `--yes` to proceed against a real key, D2).

The run is idempotent per release and grade: a second `--real` run appends a new file with a timestamp; the gate reads the newest.

**The record as built (36a, 2026-10-04; `lib/schemas/goldenRun.ts`).** A run file's first line is a header (`{ run: "golden", release, grade, startedAt, partial }`) and every other line one item, read by a strict schema. Against the sketch above: `claims: { total, notFound, substituted }` replaces the single `substituted`, because P2.1a needs the two apart; `frontier: [{ kind: "assistant" | "grading", cacheRead }]`, one entry per call in order, replaces `frontierCalls` and `cacheRead`, because "a hit on every call after the first" cannot be read from a sum; and `refusalCause`, `code`, `messageId`, `traceId`, `language`, `graderCriteria` (the four as booleans, null when not graded), `prefixSha256` (named `promptSha256` until 36b) and `costUsd` are added, each read by a criterion or by a label. A line holds no question and no answer text.

**The run as built (36b, 2026-10-04; `lib/gate/goldenRun.ts`, `workers/gate/`, `scripts/golden-run.ts`).** `npm run gate:golden -- --stub | --real --user <e-mail> [--yes] [--limit <n>]`. `runGolden` does not know how a turn travels: it is given four functions (open a conversation, ask, read the turn's gateway calls, read the answer's prefix hash), which `workers/gate/goldenDeps.ts` builds for both grades, and it returns the lines in the golden set's order whatever order the turns finish in. A turn that fails with `BUDGET_EXCEEDED` stops the run: the turns in flight finish, no new one starts, and the file says `partial` (§ 7). The file is rewritten after every item, so a run that dies leaves what it had. Decided where the paragraphs above left room, and where they are not what was built:

- **The stub grade depends on nothing that is running.** `workers/gate/stubStack.ts` starts the workers' server and the stub gateway inside the command's own process, with secrets made for that run; the database is the real one and the turns are real turns (the route, retrieval, the flow, the sensors, the rows). The stub cannot judge scope, so for an item whose label is `R-SCOPE` the classifier's answer is set through the stub's own header switch; every other refusal is the flow's rule. The run's gateway calls are kept in memory and not in `BudgetLedger`, whose rows can never be removed. Its conversations belong to `gate-stub@harness-bible.local`, and each stub run replaces the previous one's. The `ANSWER` ledger records stay, as every record does: a stub run appends 301 to the development chain.
- **The real grade runs as a named account, not as a gate principal with an `hb-gate` label.** `BudgetLedger` has no purpose column, and a label would be a migration to say what an account already says: the run's rows are the rows of the account `--user` names, and its meter is the only one they appear on. An account made for the gate keeps the spend apart from any reader's. Without `--yes` the command prints two lines and runs nothing (D2): the estimate, and what the account's cap still covers this month, so a run the cap cannot cover is known before it is paid for. The estimate is the newest real run's mean per item; else (since 36c-1, `estimateOf`) the larger of the newest stub run's prompts priced by `prices.ts` and the principal's paid turns of the last thirty days, with the lower one named beside it, because an estimate that turns out low is the one that stops a run half-way; else the command says it has no basis. `--limit <n>` runs the first n items as a pilot; its file says `partial` and, since 36c-1, is named `…-pilot-<grade>…` so that the gate does not read it.
- **The files.** The stub grade keeps one file per release, replaced by each run; every real run keeps its own, `golden-run-<release>-real-<UTC timestamp>.jsonl`, because a label names the file its answer is in. The header gained `userId`, the account the run's rows belong to, which `gate:show` and the gate's checks read them as. `pipeline/reports/` is ignored by git, so a real run's file stays on the machine that made it (tracker, Open Questions).
- **`prefixSha256` is the row's `guideSha256`** (see § 3, P2.5b, corrected here).
- **`graderCriteria` is read from data, not from a sentence.** The grader's verdict now carries `failedCriteria`, the failed names joined by commas, beside its counts (`workers/agents/grader/grade.ts`); a verdict without it reads as not graded per criterion.
- **Two changes to the stub** (`infra/gateway/stub/answer.ts`), both so that it answers as a compliant model would. It cites the figure whose label the question quotes when a fenced section holds it, and the section's first figure otherwise: the golden figure questions name their figure in quotation marks, and a stub that cites another one measures nothing about them. Its lab result is cut to the schema's 240 characters: a README's first sentence can run longer, which sent 15 of the 20 lab items through a failed repair to a refusal.

## 5. Curator labels and κ (`lib/schemas/labels.ts`, `lib/gate/phase2.ts`, 36a and 36b)

`golden/assistant/labels/2026.09.jsonl`: one line per labelled answer, `{ goldenId, runFile, messageId, grounded: boolean, criteria: { supported, precise, complete, in_scope }: boolean each, labeller: "curator" | "andre", labelledAt }`. The labeller reads the answer as the reader would (the full page of 17, or `npm run gate:show -- G-0042` printing the question, the retrieved sections' ids, the claims with their citations and the grader's criteria without its verdicts, D3) and writes the line. Flagged answers of the pilot join the same file when labelled (17 § 4's calibration query lists what is unlabelled).

`cohenKappa(pairs: [boolean, boolean][])` (pure): observed agreement minus expected agreement over one minus expected, the standard two-rater binary form; `undefined` under 20 pairs. `criterionKappa` runs it per grader criterion (the grader's PASS/FAIL against the label's boolean), so a criterion below 0.6 is named in the report's note (architecture § 6.2: retired from the grader, a guide change in a later unit). The gate's P2.1b uses the binary `grounded` pair.

**As built (36a, 2026-10-04; `lib/schemas/labels.ts`).** The label is the line above, strict, with `runFile` held to a run file's name and `labeller` to `curator` or `andre`. The schema arrived with 36a rather than 36b because the κ functions are typed by it. `criterionKappa` returns `undefined` for a criterion with under twenty pairs, and the gate's note prints `n/a` for it.

**`gate:show` as built (36b, 2026-10-04; `lib/gate/show.ts`, `lib/gate/labels.ts`, `scripts/gate-show.ts`).** `npm run gate:show` prints where the labelling stands: the run it reads (the newest real run, or the stub's when there is none; `--run <file>` names another), how many of its answers are answered and graded, how many labels pair with them against the 100 the gate needs, and the next ten to read. `npm run gate:show -- G-0042` prints one answer: the question, where it was asked from and what the golden label expects; the answer's text; each citation with its section's title and, for a figure, the label and value the book prints; the four criteria, taken from the section of that name in the `grader.md` of the answer's own guide version; and the label line to complete, with `null` in place of every verdict so that a line pasted unread is refused by the labels' schema. It reads the rows as the run's account and writes nothing. Against the paragraph above:

- **It never prints the grader's reading**: no score, no verdict, no reason. It names the stored conversation's page as well and says that page shows the score, so the label is written first.
- **It prints the cited sections, not the retrieved ones.** The retrieved set is in the turn's `retrieve` log line and nowhere a later command can read; the citations are rows.
- **It says when there is nothing to label**: a refusal or a failed turn, an answer whose text the 30-day purge removed, a row that is not in this database, an answer the grader did not grade (a label of it pairs with nothing), an answer that already has a label, and any answer of a stub run.
- **`readLabels` stops at a line that is not a label** and names the file and line, so a label the gate cannot read never becomes one label fewer.
